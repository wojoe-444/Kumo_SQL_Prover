# Checking the VeriEQL benchmark pairs

[Simple eval index](README.md) · [Full reference](../../docs/evals/verieql.md)

This evaluation reads VeriEQL's benchmark query pairs, schemas, and constraints. KumoSQL uses its own deterministic prover and database generator; it does not call a language model or reuse VeriEQL's implementation.

The corpora include LeetCode solutions, pairs from equivalence research, and Calcite optimizer tests. They contain both equivalent and different queries, without gold labels in the input files.

## Read the verdict by its evidence

- **Equivalent** is an unbounded proof under the stated supported constraints and assumptions. Additional random databases cross-check it.
- **Different** includes a database satisfying the applicable constraints on which the queries return different results.
- **Unknown** means neither answer was established.

Candidate counterexamples are replayed and shuffled to avoid differences caused only by arbitrary row order or tied LIMIT choices. Some engine-sensitive cases receive additional checks with the optimizer disabled. Picks the shuffle cannot move (`ANY_VALUE` over several values, a `LIMIT` that cuts through ties) get a further check, so a difference through such a pick stays unknown. The full reference has the details.

## Why the test run is cheaper

Almost all of a run is DuckDB answering both queries on many tiny databases. The search now uses a single DuckDB thread, rewrites only the tables whose rows changed, and does not rerun a database it has already seen both queries agree on. The databases it tries are the same, so the answers are the same, with one known exception: when a query picks an arbitrary value from a group, DuckDB's pick can depend on how the table was filled, so one LeetCode pair whose refutation rested on a lucky pick is no longer refuted. Timings and the pair are in the [full reference](../../docs/evals/verieql.md); they come from one container and a sample of the pairs, not the whole corpus.

## Latest scores

On 2026-11-22 the whole LeetCode set was run again after six more batches of rules for families of spellings of one answer (shares and percentages, sums of tests, date windows, first-row subqueries, declared value checks, three last proof steps): 11,517 of 23,994 pairs are proved equivalent, none wrong. The run before it, on 2026-11-18, had 10,882 after nine proofs were removed (see below). The run took about five and a half hours and the gain was not split by batch. Two later batches (main moved while the run was going) are not in the count: on the 1,800 pairs they can reach they prove 152 more.

On 2026-11-18 the whole LeetCode set was rerun after rules for six more families of spellings of one answer were added (counts written as `UNION ALL` or `CASE` sums, an aggregate over the table's own group, joins that only ask for a match, `NOT IN` through a derived table, rounded divisions, repeated values): 10,891 of 23,994 pairs are proved equivalent (9,113 before), none lost and none wrong.

On 2026-11-12 the whole LeetCode set (23,994 pairs) was rerun: 9,022 pairs are proved equivalent (4,787 before), none wrongly. Calcite-397 went from 337 to 342 proved. The gain comes from new rules for families of spellings of one LeetCode answer (matching with `COUNT(DISTINCT ..)`, values that occur twice, `NOT IN` against the table's own key) and from other rules merged since October. Every fifth pair was never read while writing them; it is proved about as often as the others (37.3% against 37.7%). On 2026-11-16 a fix to how text is compared with dates was checked on the 883 pairs it reaches: none lost its proof and 12 more are proved; the totals here are still the whole run of 2026-11-12. Many unproved pairs agree on every generated database but differ on a NULL the databases never contain; they stay unknown. Details and the per-problem counts are in the [full reference](../../docs/evals/verieql.md).

## Constraints matter

The input can declare keys, non-NULL columns, and other restrictions. When a table declares two primary keys, each one is kept as a key of its own. A database violating those restrictions is not a valid counterexample to a conditional claim. Read which constraints the prover models and which the execution generator enforces.

Some LeetCode answers in the files lost the quotes around their text values: `THEN YES ELSE NO` where the answer said `"Yes"` and `"No"`. The database search always read such a word as text when it is no column or name in the query. The prover now reads it the same way where the word plainly stands for a value (after `THEN` or `ELSE`, in a comparison, in the select list), so these pairs can be proved and not only searched. Nothing else in the query is touched, and a word in any other place leaves the pair unproved.

Many LeetCode answers use spellings that MySQL accepts and the test database (DuckDB) rejects: grouping by a name given in the select list, a total beside ungrouped columns, `HAVING` used as a plain filter, arithmetic on true-or-false values, and a table spelled `MY_NUMBERS` where the schema says `MYNUMBERS`. Such a pair used to stay unknown because one query could not be run. The search now gives DuckDB a query that means what MySQL means, and each reading was checked against a real MySQL server on generated tables. Where MySQL's meaning depends on something the search cannot see, the query is left alone and the pair stays unknown.

One spelling ran on both databases and meant different things. Many answers write "the next day" as `date + 1`. DuckDB reads that as the next day. MySQL turns the date into a number first, so 31 January plus 1 is 20240132, which is no date, and the answer misses every player who came back on the first day of a month. An answer that uses `DATE_ADD` does count them. The search now reads `date + 1` the way MySQL does and tries month ends, so it tells such a pair apart. On the 1,193 development pairs this reaches, 570 that used to agree are now shown different, and a real MySQL server returned different rows for every one of those 570 examples. The check also turned up one old example that MySQL did not confirm (a date that DuckDB printed with a time of day), which is fixed. The limits: where the search cannot tell whether a value is a date it refuses to run the query, the whole set of pairs has not been rerun yet, and one MySQL behaviour (a date joined to a number computed in a subquery) depends on how MySQL decides to run the query, so the search does not take a side there.

The search also learned where to look for a difference in binned data (batch 24, 2026-11-23). Take calls with a length in seconds, sorted into bins of five minutes with `seconds / 60 >= 5`. Two answers that treat a call of exactly ten minutes differently only differ on a call of 600 seconds, and the search used to try small numbers and the numbers written in the queries, never 600. It now also tries the numbers where such a scaled value crosses a limit. On the 403 practice pairs this reaches, 25 that used to look equal are now shown to differ, each confirmed on a real MySQL server, and no pair lost a difference it had. The counts are in the [full reference](../../docs/evals/verieql.md).

Some answers could not be read at all, and three repairs now read them (batch 25, 2026-11-24). The files hold `&&` as `&AMP;&AMP;`, a leftover from a web page. They hold `'S' THEN 'SMALL' ELSE 'LARGE'` as one long text `'S THEN SMALL ELSE LARGE'`, with the inner quotes gone. And one problem asks for an `UPDATE` that swaps two values in a column, which is a command and not a question. The first two are put back the only way they can be read. An `UPDATE` is read as "the table it leaves behind", and two of them are the same answer when they leave the same table. That reading is used only for simple swaps where the new value is one the column is declared to hold, and it was checked 528 times against a real MySQL server. Of 68 practice pairs that are now readable, 10 are proved and 2 are shown to differ. Most of the others are swaps that differ only when the column is empty, which the files neither allow nor rule out, so they stay undecided. The limits and counts are in the [full reference](../../docs/evals/verieql.md).

Batch 26 (2026-11-24) widened four readings in the prover: joins written with `USING`, a `GROUP BY` name that two joined tables share, the earliest or latest date compared with a fixed day, and a `WITH` table that lists its column names. About 2,100 pairs contain one of those shapes. They were run before and after: 57 pairs that only agreed on every test database are now proved, and no other pair changed. Most are answers to one problem that groups sales by a product id both joined tables have. On the usual sample of every 24th pair the proved count went from 531 to 536. The whole set was not run again. Counts by problem are in the [full reference](../../docs/evals/verieql.md).

Batches 27 to 30 (2026-11-25) added fifteen rules that run as one more last step of a proof. About 3,100 pairs contain a shape one of them reads. They were run before and after: 110 pairs that only agreed on every test database are now proved, and no other pair changed. Most are answers to one problem that turns rows of (product, store, price) into one row per product with a column per store. The step also costs time. A first version ran the whole step for any answer that writes `IF`, which is a large share of them, and four times as many pairs ran into the 30-second limit; one pair even lost its counterexample that way. Now such a pair gets one attempt of the step, and the total time is 9% above what it was before the batches. On the usual sample of every 24th pair the proved count went from 536 to 539. The whole set was not run again. Counts by problem and the time numbers are in the [full reference](../../docs/evals/verieql.md).

Some schemas say that one date comes before another, such as a login before its logout. The prover is now told this, but only for a pair of queries that does nothing with those dates except compare them. The reason is that the prover treats the fact as one about numbers, and a query that adds a day to a date or reads it as text would see the difference between a date and a number. For a pair that only compares, there is none.

The full guide documents translation, constraint handling, known non-equivalent pairs, commands, and separate proof/executed score rows. [Bounded verification](bounded-verification.md) covers KumoSQL's separate row-limited checker, inspired by the bounded approach used in VeriEQL's research.

On 2026-11-18 the checker learned that in MySQL, SQLite and DuckDB a true-or-false condition is the number 1 or 0. Of the pairs that compare a condition with something, none lost a proof and 39 more are now proved, each double-checked on 1,000 further databases. The 9,022 above is not recounted yet.

Also on 2026-11-18 the checker stopped trusting one MySQL habit: a ratio or average that passes through a subquery in the `FROM` clause (or a `WITH` query) is stored with four decimals, so rounding it again later can give a different answer than rounding it once. Ten earlier proofs depended on ignoring that and were removed, so LeetCode is 10,882 and Calcite-397 is 341 (not 342). Two of the LeetCode shapes were checked on a real MySQL with made-up tables and really do differ. Details: [the eval page](../../docs/evals/verieql.md).
