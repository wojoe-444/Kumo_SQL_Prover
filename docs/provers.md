# Equivalence provers

[Plain-language version](../docs_simple/provers.md)

> Commands written `python -m kumosql ...` belong to [KumoSQL](https://github.com/wojoe-444/KumoSQL); with KumoSQL installed they run this package. This repository's own entry points are `python -m kumo_sql_prover smt` and `python -m kumo_sql_prover sqlsolver`.

The equivalence checks behind every verified rewrite, from the structural prover to Z3, the algebraic prover and SQLSolver.

The [singleton aggregation and set identity bridges](singleton-and-set-identity.md)
cover key-fixed zero-or-one-row joins and deterministic set trees differing in
scoped relation aliases. String singleton joins report an explicit collation
condition; normalization without an assumption collector refuses that rewrite.

**Network.** None of these checks reaches the network. Calling a prover, a rewrite or a pipeline analysis from Python makes no request: the one optional library lookup, the columns of tables a project does not define (`SELECT *` over them), is off by default and needs an explicit opt-in (`KUMOSQL_SCHEMA_FETCH=1`, `--fetch-schema` on `python -m kumosql pipeline-report`, or the Settings checkbox in the local UI); see [whole-pipeline analysis](https://github.com/wojoe-444/KumoSQL/blob/master/docs/pipeline-analysis.md). BigQuery dry runs and planner checks are likewise opt-in calls.

## Conservative SQL equivalence

`kumo_sql_prover.prove_equivalent(left_sql, right_sql)` returns `proven_equivalent` only when both inputs are strict, single-query BigQuery statements whose normalized ASTs match after relational subquery lifting (a derived table that reads the query around it, or a name a nested `WITH` defines, is not lifted). By default it compares result bags, so unspecified row order is ignored. With `ignore_row_order=False` (`--respect-row-order`) both queries must also end in the same `ORDER BY`; nothing shows its keys are unique, so rows tied on them may still come back in a different order, as on any two runs of either query.

Root CTEs are renamed by position after being put in a canonical dependency order, so CTE order alone does not block a proof; reordering is skipped for recursive WITH, forward references, or names that differ only in case.

The subquery lifting that precedes the comparison keeps a derived table in place when its body reads a column of an enclosing query or a name a nested `WITH` defines, and compares it where it stands (see [subquery lifting](https://github.com/wojoe-444/KumoSQL/blob/master/docs/rewrite-rules.md#subquery-lifting)). Inlining a `WITH` table is declined when its body reads a name that a `WITH` around a use of it redefines, because the inlined copy would read the other relation.

SQL comments (`--`, `#` and `/* */`) never block a proof: the structural check drops them before comparing ([`tests/test_audit1002_static_comments.py`](https://github.com/wojoe-444/KumoSQL/blob/master/tests/test_audit1002_static_comments.py)). A comment holding a Dataform `${...}` expression (or its masked placeholder) is kept and compared, because Dataform expands expressions inside comments and a line break in the expansion ends the comment and becomes SQL.

Before comparing, the prover also removes grouping parentheses, flattens `AND`/`OR` chains, removes `TRUE` from `AND` and `FALSE` from `OR` in filter and join conditions, drops `WHERE TRUE`, merges root CTEs with identical bodies, and drops unreferenced CTEs. The subquery lifting, the predicate step, the CTE steps (renaming, reordering, merging, dropping), the parenthesis stripping and the redundant-DISTINCT dropping are re-derived by independent checkers that share no code with the cleanup rules or the prover; if one refuses, the pair is `not_proven`, and accepted steps are listed in `result.proof_checks` ([proof safeguards](proof-safeguards.md)). The structural prover never qualifies columns in this normalization. The algebraic and SMT provers do resolve bare columns themselves (which FROM item owns an unqualified name, with a schema or by elimination), and an independent reader re-derives each owner they choose from the query text: the SMT compiler's choice for every bare column, its one-table qualification, the algebraic normalizer's two qualification passes and the scoped-identity check. A disagreement (another owner, a select alias read as a column, a name two sources share) makes the pair `not_proven`; a column the text cannot settle is left to the prover ([the provers' own column resolution](proof-safeguards.md#the-provers-own-column-resolution)). The `qualify_columns` rule's own step is checked independently by the acceptance layer ([column qualification](proof-safeguards.md#column-qualification)).

It refuses to prove queries containing windows that depend on how ties are broken, tie-sensitive or approximate (`APPROX_*`) aggregates, `TABLESAMPLE`, or a `LIMIT`/`OFFSET`, unless both queries end in the same `ORDER BY ... LIMIT` over output columns. Volatile calls (`RAND()`, `CURRENT_*`, `GENERATE_UUID()`, `SESSION_USER()` and every other call on the [shared list](#volatile-calls)) and calls that may be user-defined functions are accepted only when left identical and in place. A user-defined function name is compared exactly, since BigQuery reads it case-sensitively; built-in function names are compared in any case. Under bag semantics a root `ORDER BY` is dropped only when no key can raise an error: columns, literals, comparisons, or an expression the SELECT list already computes. This holds when a `LIMIT` that cannot cut any row is stripped first: the `ORDER BY` stays until the same check passes. Structural differences are reported as `not_proven`, never as a proof of inequivalence. This is intentional: false negatives are acceptable; false positives are not.

It also refuses a query BigQuery would reject, found without a schema (`src/kumo_sql_prover/input_validity.py`): a `HAVING` with no `GROUP BY` and no aggregate, or a column that a derived table or CTE with fully known outputs does not produce. Matching trees prove nothing about results when there is nothing that runs, and each shape is confirmed against a BigQuery dry run. A type BigQuery does not have (`FLOAT`, `INT32`, `UUID`, `DOUBLE`, `VARCHAR`, ...), in a cast, an `ARRAY<...>` or `STRUCT<...>`, a typed literal or a script's column list, is refused in the structural, SMT, algebraic and SQLSolver provers, the statement-level proofs, the bounded check and the counterexample searches, because sqlglot prints those names as valid BigQuery types ([the list of entry points](proof-safeguards.md#type-names-bigquery-rejects)). Only these shapes are caught; see [Rewrite rules](https://github.com/wojoe-444/KumoSQL/blob/master/docs/rewrite-rules.md#inputs-bigquery-would-reject).

For audit or optional execution, `result.verifier_sql` contains a BigQuery query that counts JSON-encoded result rows on each side and compares their multiplicities with a full outer join; it compares bags even when row order is respected. The verifier is an execution artifact and does not override the static safety checks.

```python
from kumo_sql_prover import prove_equivalent

result = prove_equivalent(
    "SELECT id FROM (SELECT id FROM `p.d.customers`) AS c",
    "WITH base AS (SELECT id FROM `p.d.customers`) SELECT id FROM base AS c",
)
assert result.proven
```

CLI usage:

```shell
python -m kumosql prove-sql-equivalent left.sql right.sql --verifier-sql verify.sql
```

The command runs the structural proof first and, when row order does not matter, the SMT-based prover (with the algebraic normalizer, see below) for what the structure check cannot see: a CTE against an inline subquery, a `LIKE` that another `LIKE` covers, `USING` against `ON`, an unused aggregate column. A proof from the second step says `SMT proof:` and lists its assumptions as `assumption:` lines. A pair it cannot prove stays `not_proven`, even when the SMT-based prover finds a counterexample; run `prove-sql-smt` to see that.

Two `CREATE [OR REPLACE] TABLE|VIEW name AS query` statements are compared as a write whose query is analysed (`kumo_sql_prover.statement_proof`): everything except the query (kind, name, `OR REPLACE`, `TEMP`, partitioning, clustering, options) must match as text, and the two queries must be proven. Functions, procedures, scripts and a `CREATE` without a query are not unwrapped.

## Result equivalence on synthetic data

The static prover only accepts rewrites whose normalized ASTs match. To test rewrites it cannot prove, `kumo_sql_prover.check_result_equivalence(left_sql, right_sql, schema)` runs both sides against the same deterministic synthetic tables in a local DuckDB engine (BigQuery SQL is translated with `sqlglot`, then pinned to BigQuery's semantics, see [Running BigQuery SQL on DuckDB](bigquery-on-duckdb.md)) and compares the results as multisets, including column names.

- Seed 0 is always empty tables. On other seeds each value is NULL with probability `null_rate` (default 0.15, so a small table can come out with no NULLs at all), every non-empty table without a declared key gets one exact duplicate row, and values come from small domains so joins and groups collide.
- Every run gets a fresh in-memory connection. Tables written by a script (`CREATE TABLE ... AS`, `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`) are renamed to run-unique local names, and the final written table is compared when the script does not end in a query: an `UPDATE` or `DELETE` is compared by the rows it leaves, never by its affected-row count. Writes that cannot be compared faithfully are reported as `error`: `MERGE` and `UPDATE ... FROM` (BigQuery fails when a target row matches several source rows, DuckDB silently uses one), `UPDATE` or `DELETE` without the `WHERE` clause BigQuery requires, and a modifying statement whose table cannot be identified.
- Dataform SQLX is supported: blocks are dropped and `${ref(...)}` becomes a table name. Any other interpolation, unknown table, or execution failure is reported as `error`, never as equivalent.
- A mismatch returns `different` with the failing seed and the rows only one side produced. Agreement is evidence, not a proof, and it is weaker than BigQuery agreement: the queries run on DuckDB after translation, floats are compared to 12 significant digits, column names are compared without case, and result column types are not compared (`SELECT 1` and `SELECT 1.0` agree).
- Values keep their kind: `TRUE` never equals `1`, NaN never equals the string or array `"NaN"`, and a struct never equals an array of key/value pairs, at any nesting depth. Integers, floats and decimals still compare by value, since DuckDB's result types differ from BigQuery's (and between equivalent queries). Floats are rounded to 12 significant digits by default; `float_digits=None` compares them exactly and `float_digits=N` sets another precision. `booleans_are_integers=True` (on `compare_outputs` and `find_targeted_difference`) reads `TRUE` as `1` for corpora written for MySQL or Calcite, which have no boolean type; the SQLSolver, QED and Cosette benchmarks use it. The policy used is recorded on the result (`result.float_digits`) and printed by `describe()`.
- Data generation is seeded and repeatable: the same schema and seed always produce the same rows (a test pins a digest of a small dataset, so a change to the value domains or draw order fails loudly). Column order in the schema mapping is part of the input.
- Each side is executed twice per seed on identical data. A side that differs from itself (for example `RAND()` or `GENERATE_UUID()`) makes the result `inconclusive`, naming the side and seed, instead of a false `different` or `equivalent`. Failures while fetching results are reported as `error`.

```python
from kumo_sql_prover import assert_result_equivalent, lift_subqueries

schema = {"p.d.orders": {"customer_id": "INT64", "amount": "FLOAT64"}}
original = "SELECT * FROM (SELECT customer_id, SUM(amount) AS total FROM `p.d.orders` GROUP BY 1) AS t"
assert_result_equivalent(original, lift_subqueries(original).sql, schema)
```

### Recording synthetic evidence on a rewrite result

`attach_synthetic_check(result, schema, seeds=range(8))` (or `python -m kumosql rewrite-sql --synthetic-check --synthetic-schema schema.json [--synthetic-seeds N]`) runs the harness on a changed `apply_rules` result and records one `synthetic_results` check. It is opt in; ordinary rewriting never executes anything. `schema` maps each source table as written in the SQL to its columns and BigQuery types.

| Outcome | Meaning | Effect on the label |
|---|---|---|
| `passed` | Outputs matched on every seed | None. Agreement is evidence, not proof: an unproven result stays `unproven`, is never `trusted`, and `proven` is untouched. `summarize_evidence` counts it as `synthetic_agreed` and useful evidence. |
| `failed` | A counterexample was found | The result drops to `unproven` (a proven result too, since a disagreeing input contradicts it). The check names the failing seed, the difference kind, row counts and up to three synthetic rows per side; it never contains query text or column names. |
| `inconclusive` | A query differs from itself on identical data (`RAND()`, `GENERATE_UUID()`) | None. |
| `not_run` | Nothing was compared: duckdb missing (`kumosql[execution]`), output unchanged, a rule failed, an unsupported column type, or a query that cannot be translated or executed locally | None. |

Every outcome records `seeds`, `seeds_checked`, `failing_seed`, `rows_per_table`, `null_rate` and the engine version, so a failure reproduces with `generate_synthetic_dataset(schema, seed=<failing_seed>)`. Attaching again replaces the earlier synthetic check.

Install the engine with `pip install -e ".[execution]"` (it is included in `.[dev]`). `tests/test_result_equivalence.py` runs every lifted query in its corpus through the harness (and fails if fewer than 9 of the corpus's proven lifts were executed, so a prover that declines everything cannot pass it) and checks that deliberately broken rewrites are caught.

## SMT equivalence prover

`kumo_sql_prover.prove_equivalent_smt(left_sql, right_sql)` proves semantic equivalence with Z3 instead of comparing syntax, so it accepts rewrites such as filter pushdown into a CTE, join reordering, `DISTINCT` to `GROUP BY`, `CASE` to `IF`, redundant predicates, and self-join elimination under `DISTINCT`. Install it with the optional extra: `pip install -e ".[smt]"`.

It models inner and cross joins, `WHERE`, derived tables and CTEs, `GROUP BY`/`HAVING` with `COUNT`, `SUM`, `MIN`, `MAX`, `AVG`, `COUNTIF`, `LOGICAL_AND`/`LOGICAL_OR`, `UNION ALL`/`UNION DISTINCT`, `SELECT DISTINCT`, and NULLs with three-valued logic. Other deterministic functions are uninterpreted: equal inputs give equal outputs. A pair that holds a [volatile call](#volatile-calls) is never proven, and a proof that reads a function the prover does not know this way lists it as an assumption. `UNION ... BY NAME` and `CORRESPONDING` are rewritten to the positional form first (`kumo_sql_prover.set_operations`); when a branch's columns are not known (`SELECT *`, duplicate names) or differ under a plain `BY NAME`, the result is `not_proven`. Anything else (outer joins, windows, `LIMIT`, predicate subqueries, nondeterministic functions) returns `not_proven`.

The result is one of:

- `proven_equivalent`: the two queries return the same bag of rows on every database, under the listed `assumptions` (no NaN, runtime errors not modeled, column types not compared).
- `not_equivalent`: `counterexample.tables` is a small database on which the queries return different rows (`left_rows`, `right_rows`). It is only reported when no uninterpreted function is involved.
- `not_proven`: outside the subset, or no proof was found.
- `proven_conditionally`: only with `conditional=True` (the `--conditional` flag, **Compare queries**): the pair is equivalent on every database where the listed `conditions` hold, such as "`users.id` is a non-NULL primary key". It is a proof under those conditions, never counted as `proven_equivalent`; see [Equivalent under conditions](conditional-equivalence.md).

SMT counterexample models are extracted in a fresh Z3 context so earlier calls and unrelated imports do not change the candidate's unconstrained values. For example, removing an inner lookup join when `users.plan` may be NULL consistently finds a user with a NULL plan, even with a foreign key and a unique lookup key. Candidate search remains incomplete and bounded by the solver timeout; every returned database must satisfy the declared constraints and produce different result bags. This isolation does not change the proof conditions.

A returned database is also one the tables can hold and an engine would read the same way (`tests/test_counterexample_types.py`, `tests/test_counterexample_string_order.py`, `tests/test_counterexample_time_limit.py`):

- **Values fit the declared column types.** The solver's values carry no column type, and the search used to prefer "every value is a number", so a counterexample could show the number 1 in a `STRING` column or `'A'` in an `INT64` key. The search now asks for a value of the declared type first (a string for `STRING`, a whole number for `INT64`, a number for `NUMERIC`, `BIGNUMERIC` and `FLOAT64`) and drops a candidate that still does not fit. Columns with no declared type keep the old preference for whole numbers.
- **Strings are in their real order.** The provers order strings by an uninterpreted rank and state only the order of the queries' own string literals, which is all a proof needs. A model of a difference may rank any other string as it likes, and the search evaluated both queries through that model: `WHERE s < ''` against `WHERE 1 = 0` came back `not_equivalent` with `s = 'A'`, although no string is below the empty one and the pair is equal on every `STRING` column, and `WHERE s < 'b' AND s > 'a'` was shown to keep the row `s = ''`. The search now drops a candidate unless the model ranks the database's strings, the queries' literals and every other string it ranked in code point order (how BigQuery and DuckDB compare strings). Before giving up it tells the solver the real order of the strings it chose and asks again, twice, and then offers a small set of strings whose order is stated in full: the literals and up to two strings from each gap between them (`'aa'` between `'a'` and `'b'`; the next day between two dates, since the column may be a `DATE`). A difference that needs a string the set lacks (one between `'a'` and `'a '`, say) stays `not_proven`.
- **The search keeps to the time limit.** Each preference used to be tried with `push` and `pop` on the solver that had found the difference. `push` moves Z3 to its incremental core, which neither `timeout_ms` nor the work cap covers, and with about ninety string literals in the queries it did not return (z3 4.16 and 5.4). Each preference now gets a fresh solver with the same limits.

Limits: a column with no declared type may still be shown holding a number where the queries compare it with a string (the provers order a number below any string there, as SQLite does, and BigQuery would reject the comparison), and string order is code point order, so a counterexample for a case-insensitive MySQL or PostgreSQL collation may not separate the queries there. Measured on 600 generated pairs of `tools/soundness_fuzz.py` (seed 11) with both provers: the same proofs before and after. Before, 135 counterexamples, of which 4 held a value of the wrong type and 1 (a `s < ''` filter) did not separate its pair; after, 139, every one loading into DuckDB tables of the declared types and separating its pair there with the optimizer off. The one wrong refutation became `not_proven` and five pairs that had no usable candidate gained a counterexample.

**Executed counterexamples.** The solver's model gives no counterexample for outer joins, duplicate-producing joins, `NOT IN` with NULLs or set operations of different shapes, so such pairs used to stay `not_proven`. `prove_equivalent_algebraic(..., search_counterexample=True)` (on for **Compare queries** and `POST /api/prove-queries`) then runs both queries on the corner-case, targeted and random databases of `kumo_sql_prover.targeted_data`, built around both queries and respecting declared NOT NULL columns, keys and foreign keys, and returns the first database on which the result bags differ, shrunk row by row, as a `not_equivalent` counterexample (`src/kumo_sql_prover/executed_refutation.py`). It is a refutation that needs no trust in the prover: anyone can replay it. To keep it a refutation of the BigQuery queries rather than of DuckDB's reading of them, the search runs only when every column type is declared, both queries stay within an allow-list whose DuckDB translation evaluates as in BigQuery (joins, set operations, subqueries, comparisons, arithmetic, `CASE`/`IF`/`COALESCE`, plain aggregates and aggregate windows; no `LIMIT`, string or date functions, `LIKE`, arrays, `ROW_NUMBER` or nondeterministic functions), the DuckDB run follows BigQuery's semantics or fails where BigQuery fails ([Running BigQuery SQL on DuckDB](bigquery-on-duckdb.md)), and the difference survives rounding floats to 6 digits and reversing every table's rows. Finding nothing proves nothing.

#### Executed counterexamples for DuckDB queries

With `dialect="duckdb"` the same option searches too (`src/kumo_sql_prover/duckdb_refutation.py`). A query written for DuckDB needs no faithful reading, since DuckDB is its own reference: the candidate databases are built the same way (from the BigQuery spelling sqlglot gives the two queries, which only steers the search), and one is accepted only when the two queries **as written** return different bags on tables created with the declared DuckDB column types. The search runs only when both queries stay inside a list of constructs with one answer per database: joins, set operations, subqueries, comparisons, arithmetic, `CASE`/`COALESCE`/`NULLIF`, casts, plain aggregates and aggregate windows with the default frame. It does not run a query with `LIMIT`, `OFFSET` or `FETCH`, `DISTINCT ON`, a `ROWS` or `GROUPS` frame, a ranking or navigation window function, any function outside the list (nothing random, nothing that reads the clock or a file), or a table that is neither declared nor a CTE; the connection has external access switched off. A difference counts when it survives rounding floats to 6 digits, each side returns the same bag with every table's rows reversed, and both queries return the same rows with DuckDB's optimizer off. A pair that reads no table is decided by one run of each query. No other dialect is searched. `tests/test_duckdb_refutation.py` holds pairs that must be refuted with a database that replays, equivalent pairs that must not be, and the queries the search must refuse. The [optimizer wrong-result bugs](evals/optimizer-bugs.md) eval uses it.

```python
from kumo_sql_prover import prove_equivalent_smt

result = prove_equivalent_smt(
    "SELECT id FROM (SELECT id, a FROM t WHERE a = 1) AS s WHERE id > 0",
    "WITH s AS (SELECT id, a FROM t WHERE id > 0) SELECT id FROM s WHERE a = 1",
)
assert result.proven
```

Pass `schema={"t": ["id", "a"]}` to enable `SELECT *` and unqualified columns in joins, and `exact_arithmetic=True` to reason about `+`, `-` and `*` exactly (right for INT64 and NUMERIC, not FLOAT64). `group_by_constants=True` reads a literal in `GROUP BY` as a constant (Calcite's rule) instead of a column ordinal. The CLI prints JSON and exits 0 only on a proof:

```shell
python -m kumo_sql_prover smt left.sql right.sql --schema schema.json
```

The command runs the algebraic normalizer in front of the solver (the same prover as **Compare queries**) and unwraps `CREATE TABLE|VIEW ... AS` statements as described above. Without a schema it still handles `LEFT`/`RIGHT`/`FULL` joins (the unmatched side reads as NULL in every column; `SELECT *` over it needs the schema), `JOIN ... USING (k)` for a select that lists its columns, and a `LIKE 'ab%'` test beside `LIKE 'a%'` on the same column (patterns that are a literal with one trailing `%`; `_`, escapes and `ILIKE` are left alone).

With a schema, `* EXCEPT (..)`, `* REPLACE (e AS c)` and `* RENAME (c AS d)` on `*` or `t.*` apply in that order. A modifier naming a column the star lacks or lists twice (`* EXCEPT (id)` over a join of two tables with an `id`), a `RENAME` onto a name the star already has, and `* ILIKE` are `not_proven`. Until 2026-10 the prover ignored `RENAME` and `ILIKE` on `*`, `EXCEPT` too under sqlglot 30 (which renamed its argument), and every modifier on `t.*`, and the algebraic prover read `SELECT * EXCEPT (..) FROM (q) AS s` as `q`, so `SELECT * EXCEPT (b) FROM t` was proved equal to `SELECT * FROM t`; the bounded checker, which ignored them too, now declines any star modifier.

`tests/test_smt_fuzz.py` checks the prover against SQLite on random queries and databases: every proof must hold and every counterexample must separate the queries. Its 250 pairs (a random query and either a one-site text rewrite of it or a second random query) are generated before the prover runs and pinned by a sha256 in the test; each proven pair's 25 validation databases come from an RNG seeded by the pair's index, so a different solver outcome cannot change later pairs. A rewrite that does not apply leaves two identical queries: those 108 identity pairs must all be proven, and the floors count only the 142 changed pairs (measured 2026-10-03: 32 proven, 23 of them the trivial `WHERE TRUE AND`; 79 refuted; 31 not proven, all pairs of two random queries). The floors are 28 changed proofs, 7 of them outside `WHERE TRUE AND`, and 70 refutations. Not-proven pairs have no truth label, so the counts are coverage floors, not accuracy.

**Threads.** Z3 terms share one global context that is not thread-safe, so the SMT, algebraic and bounded provers and the rules that call Z3 hold one re-entrant lock (`kumo_sql_prover.solver_lock`): proofs from UI requests and background analyses run one at a time instead of corrupting the context.

**Work cap.** Besides the wall-clock `timeout_ms`, every solver check of the SMT, algebraic and bounded provers (the bounded checker's search and its `evaluate` helper included) gets a deterministic work cap (Z3's `rlimit`, `timeout_ms × 20,000` units; `kumo_sql_prover.solver_lock.bounded_solver`), sized well above the largest check that finishes on the QED pairs. A check stopped by the cap stops at the same point on every machine and the result says the solver "ran out of its work budget"; "timed out" means the wall clock stopped it, so a faster or idler machine might decide it; with a very small `timeout_ms` the clock usually stops a check first, so whether such a pair is proven or unknown can vary with machine load (it never flips between a proof and a refutation). Calls made in one process share Z3's context, so a check right at its limit can still go either way after other proofs ran.

**Limits and bad input.** The solver's `timeout_ms` covers each solver check, not the work around it, so that work is bounded separately: row mappings are enumerated lazily up to 5,000; a query that reads more than 256 tables once its CTEs are expanded (a CTE read twice per level doubles each level) is declined by every prover, and the SMT compiler stops past 4,000 selects and table reads; numeric literals longer than 100 characters or outside FLOAT64's exponent range (`1e100000000`) are declined at every entry point, including a query compared with itself. Text that cannot be tokenized, a non-integer `GROUP BY`, `ORDER BY` position or `LIMIT`, and nesting too deep for the compiler are `not_proven`, never an exception; a wrongly typed option (`timeout_ms="x"`, a schema entry that is not a column list) raises `TypeError`/`ValueError`. Schema, types and constraints entries whose table names differ only in case and disagree are dropped rather than one winning by insertion order (the bounded checker's `schema_from_prover` does the same, so such a schema gives "unsupported: table is not in the schema" rather than a DuckDB error; entries that agree up to case are one table), and uninterpreted functions are named from their arguments in declared order, so a node's construction order does not change a verdict.

**Cost of a long expression.** `timeout_ms` is a limit on each solver check, so what a proof costs follows the number of checks and the work before them. Two things made a sum cost far more than its length, and both are gone (`tests/test_long_sums.py`).

- *Compiling.* `c0 + c1 + .. + cn` asked for the type of the whole sum again at every `+`, so four hundred terms took twenty seconds before the solver started. The compiler now keeps the type of an arithmetic node while it compiles the operands of the outermost one (`_Compiler._operands`), and drops what it kept when that is done or a select names a new alias.
- *Comparing errors.* Each `+`, `-` or `*` is an operation that may overflow, and it was compared with the other query's operations by two solver checks whose formulas held every operand before it, each in a canonical order. A sum of ten columns compared with itself took four to five seconds, and forty columns one to two minutes. Both checks are now asked without what is inside the operands where that cannot change the answer (`smt_errors.abstracted`): each outermost application of an uninterpreted function (the value `Add(..)` of the sum so far, an unknown failure `fails:Add(..)`) is read as a free constant. A question that cannot hold in that reading cannot hold as written, always; and when the replaced terms are applications of different functions the two readings hold in the same cases, because nothing else constrains the functions. So "can this operation run and fail?" is answered from the short reading whenever it is exact, and "does the other query fail there too?" is tried there first and put to the solver in full only when the short reading leaves it open. That second question is also put first to the up to four operations of the same kind and text nearest in order, which cover the operation whenever all of them do, and "the operands are known" is said of the operands as written and not of their canonical order (the same condition).

Measured on one machine, a sum compared with itself, `timeout_ms=1000`: ten columns 4.2 s before and 0.7 s after with no declared types, 5.3 s and 0.8 s declared INT64; forty columns 58 s and 2 s, and 105 s and 3 s; a hundred columns 220 s and 6 s with no types, more than 200 s and 14 s declared INT64. The verdicts are the same, except that the forty-column INT64 comparison used to end in `unknown` on a solver limit and is now `same`. What is left: there are still one or two checks for each operation, the compiler and the formulas still grow with the expression before them (four hundred columns take about a minute), and two queries whose operations differ in shape are compared in full, so a very long expression can still take many times `timeout_ms`.

**Unmodeled arguments.** The SMT compiler declines any sqlglot argument it does not model (`src/kumo_sql_prover/smt_args.py`, `check_args`, called next to `check_modeled`): a `SELECT`, set operation, derived table, `JOIN`, table, column, `ORDER BY` item, `DISTINCT` or `CAST` that carries an argument outside that node type's allowlist is `UnmodeledConstruct`, and `*` takes no modifier. This covers `CAST(.. DEFAULT .. ON CONVERSION ERROR)`, `FOR UPDATE`, `CLUSTER BY`, `SETTINGS`, `SELECT` modifiers such as `SQL_CALC_FOUND_ROWS` and join hints, including clauses that cannot change a result: the guard does not argue which ignored clauses are harmless. A newly modeled argument has to be added to the allowlist, so forgetting it declines a proof instead of proving a wrong pair. Generic functions are not listed because every argument is part of their uninterpreted function's name. `tests/test_soundness_smt_args.py` has the pairs.

**Solver in rewrite verification.** `verify_rewrite` also hands any changed statement to the algebraic prover (the section below), so a rewrite beyond predicates (a removed self-join, a pushed-down aggregate) can be `proven`. The solver is on by default; **Settings → Solver** (or `GET`/`PUT /api/prover`) turns it off and sets the time limit per check (500 to 60000 ms, default 5000). It assumes only what is declared: `REQUIRED` columns and a primary key from the saved BigQuery catalog, and the `assertions` (`nonNull`, `uniqueKey`, `uniqueKeys`) of the loaded Dataform project, plus the columns of each model's SELECT. Neither BigQuery nor Dataform enforces these when data is written, so a proof that used them lists that as an assumption.

**Saved equivalences across layers.** Tell KumoSQL that two tables hold the same data under different names ("column `amt` of `raw.orders` is column `amount` of `raw.orders_v2`") and the proofs use it, including many layers down a pipeline. In **Settings → Solver → Equivalent columns**, or with `python -m kumosql equivalence add raw.orders raw.orders_v2 amt=amount id=order_id --whole`, save the pair; list columns only (the listed columns hold the same rows, so it applies to queries that read nothing else from the second table) or tick *same rows* for the whole table. They are stored in the data folder (`equivalences.json`), never written to BigQuery, and used as an assumption that proofs list. Rewrite verification applies them automatically. **Compare tables** in the same page, `POST /api/prove-tables` and `python -m kumosql prove-tables LEFT RIGHT --project DIR` prove two models of a pipeline equivalent: models are matched layer by layer from the sources up, each match becoming a lemma for the layers above (so one declaration on a source ripples up through every layer built on it), and when the pipelines are cut at different places the models are inlined as derived tables and the flat queries compared. A model is read as its query only when its table holds exactly what one run of that query returns: an incremental model, one with pre or post operations, a script (several statements, or one that is not a query) and one whose values change from run to run (a clock, `RAND`, a UUID) equals only itself, so two such models with the same SQL are not matched and none is inlined. Two models with the same SQL are matched without the solver only when nothing in it depends on row order or ties (`LIMIT`, `ARRAY_AGG`, `ROW_NUMBER`, ...); otherwise the solver decides, and an assumption it needs (ties in a window's `ORDER BY` resolving alike) is listed with the result. An upstream query is inlined only where no `WITH` table of the reader in scope shares the name of a table it reads. **Compare queries** (same page, `POST /api/prove-queries`) proves two pasted queries equivalent with the same declared keys, types and saved equivalences, and shows a counterexample database when they differ, one that keeps every declared fact and on which BigQuery would show the difference ([Running BigQuery SQL on DuckDB](bigquery-on-duckdb.md)). When a pair is equivalent only under some NOT NULL, unique or foreign-key facts, it lists them, each with a SQL check ([Equivalent under conditions](conditional-equivalence.md)). For a refuted pair it can also show "Equivalent except when P", a verified predicate for the rows that differ ([Difference explanations](difference-explanations.md)). Workspace and Changes list the assumptions a proof relied on under its checks.

### Numbers and runtime errors

With declared column types (`types={"t": {"x": "INT64", "f": "FLOAT64"}}`, or the saved BigQuery catalog) the prover reads numbers the way BigQuery does (`src/kumo_sql_prover/smt_values.py`) and tracks the operations that can fail (`src/kumo_sql_prover/smt_errors.py`). Without types the old reading stays: every number is one rational, and a pair is proved under the "runtime errors are not modeled" assumption.

**Values.** A decimal or exponent literal is a FLOAT64 unless it is typed with a NUMERIC or BIGNUMERIC operand (next paragraph), so it stands for the double nearest its text (`0.1` and `0.10000000000000001` are one number, `1e-324 < 2e-324` is FALSE) and `0.1 + 0.2 = 0.3` is FALSE; an integer literal is an INT64, range-checked (`-9223372036854775808` included). Arithmetic over literals is folded as BigQuery evaluates it (INT64 exact, FLOAT64 as a double, `/` always FLOAT64). An INT64 column is whole and bounded, so `x > 5` and `x >= 6` are one condition; an INT64 literal past 2**53 is only modelled where no FLOAT64 value is in the queries, and literals outside FLOAT64's range or with an exponent far outside it are declined. A query that can tell `-0.0` from `0.0` (`IEEE_DIVIDE`, `ATAN2`, `SIGN` on a FLOAT64, `CAST(f AS STRING)`) is declined. FLOAT64 arithmetic stays rational (the double a `/` returns is not modelled), so those pairs are unknown. NUMERIC and BIGNUMERIC arithmetic over values of a known scale is scaled and rounded (`src/kumo_sql_prover/smt_numeric.py`): a column declared INT64, NUMERIC or BIGNUMERIC (its values have at most nine, or 38, decimal digits and stay in range), an integer literal, a string literal of plain decimal digits cast to NUMERIC or BIGNUMERIC (`NUMERIC '1.50'` is `NUMERIC '1.5'`), and `+ - * /`, `CAST` to NUMERIC or BIGNUMERIC and `ROUND(x, k)` of such values with the result rounded half away from zero to the scale of its type (`ROUND(n * m, 9)` is `n * m`, `n / 3 * 3` is not `n`, `(n * m) * m` is not `n * (m * m)`). An INT64 factor adds no digits, so `n * 2` is `n + n`. A result outside the range (29 integer digits for NUMERIC) is an error site like an INT64 overflow, so a guard moved off a NUMERIC product is classified. Where the scale cannot be bounded (an aggregate, a `CASE`, a FLOAT64 operand, `CAST(f AS NUMERIC)`, a parameterized `NUMERIC(p, s)`) nothing is compiled and the pair stays unknown. Unverified in the GoogleSQL documentation: that `*` and `/` of NUMERIC round half away from zero (the pages state it for conversions and `ROUND`), that a `NUMERIC '..'` literal rounds like `CAST(string AS NUMERIC)`, that `ROUND(x, k)` with a negative `k` and a result past the range behaves so, and the last digit of BIGNUMERIC's range. `smt_values.py` also holds the reference arithmetic (INT64 overflow, `DIV` and `MOD`, `IEEE_DIVIDE`, `SAFE_DIVIDE`, `CAST(FLOAT64 AS INT64)`, NUMERIC rounding) that the tests and the [numeric traps eval](evals/numeric-traps.md) check the labels against; the rules the author could not confirm in the GoogleSQL documentation are marked `unverified` there.

**Literals next to NUMERIC and BIGNUMERIC** (`src/kumo_sql_prover/smt_literal_coercion.py`). BigQuery converts a decimal *literal* to the type of the operands it is combined with: next to a NUMERIC operand it is the NUMERIC nearest its text (nine decimal digits, half away from zero), next to a BIGNUMERIC operand the BIGNUMERIC nearest it (38 digits), and only otherwise the nearest double. Run on BigQuery on 2026-11-10 with inline values (zero bytes billed):

| Query | BigQuery |
| --- | --- |
| `NUMERIC '0.1' = 0.1` | TRUE |
| `NUMERIC '0.1' = 0.1000000001` | TRUE (the literal rounds to nine digits) |
| `BIGNUMERIC '0.1' = 0.10000000000000001` | FALSE (one double, two BIGNUMERIC values) |
| `NUMERIC '0.3' = 0.1 + 0.2` | FALSE (`0.1 + 0.2` is a FLOAT64 expression; the NUMERIC is converted instead) |
| `NUMERIC '0.1' = CAST(0.1 AS FLOAT64)`, `= (SELECT 0.1)` | FALSE (not literals) |
| `NUMERIC '0.1' = -(-0.1)`, `= (0.1)`, `= 1e-1` | TRUE (still literals) |

The same holds for `<`, `IN`, `BETWEEN`, `+ - *`, `COALESCE`, `IF`, `IFNULL`, `NULLIF`, a simple `CASE`, `GREATEST`, `SAFE_DIVIDE` and the columns of a `UNION ALL`. The prover used to read every such literal as the double, which proved `WHERE n = 0.1` empty for a NUMERIC `n` and `b = 0.1` equal to `b = 0.10000000000000001` for a BIGNUMERIC `b`. Now a literal whose three readings differ (`0.1`; not `0.5` or `2.25`) takes the reading of the widest operand it is typed with (INT64, NUMERIC, BIGNUMERIC, FLOAT64 in that order). When that operand's type is not declared the reading is left open: a proof must hold for every typing, so `n > 0.1` still equals `0.1 < n` with no types, while `n = 0.1` against `n = 0.10000000000000001` is neither proved nor refuted. A counterexample for undeclared columns is searched with the columns read as FLOAT64, since the database is shown as plain numbers. A literal typed with an argument of a function whose signature is not modelled gets an unknown reading per call text; a literal in a set operation whose other operand is not a plain literal or a FLOAT64 is refused, and so is a reading that does not fit its type. `tests/test_soundness_smt_literal_coercion.py` holds the pairs.

**Literals next to a column of a grouped derived table** (`src/kumo_sql_prover/derived_types.py`, 2026-11-11). A grouped derived table is kept whole and its columns are unknowns, so the type next to the literal in `i.price > 1.3 * d.avg_amt` was not known, and the reading was left open separately in each query: two queries that differed in anything else were not proved. This is the form every decorrelated `x > (SELECT 1.3 * AVG(y) ...)` takes, so TPC-H and DSB rewrites with such a filter stopped here (`2 * AVG(y)` did not: an integer literal reads the same in every type). Two things changed. The open reading is now shared by the same column of the same derived relation (same text over the same tables, so the same types) wherever it occurs, in any dialect. And on the BigQuery route the type is read where the declared types fix it: an output that is a column of a base table, or `SUM`, `MIN`, `MAX`, `AVG` or `COUNT` of one. `SUM`, `MIN` and `MAX` keep their argument's type, `AVG` of an INT64 or a FLOAT64 is a FLOAT64 and of a NUMERIC or BIGNUMERIC keeps it, `COUNT` is an INT64. With the type known the literal has one reading, so a pair whose two derived tables are written differently (`BETWEEN 80 AND 109` against two comparisons) is proved once the prover has proved the two bodies equal. A column of a nested derived table has the type of the output it names, read the same way, so the average of per-group sums in `SELECT k, AVG(s) FROM (SELECT k, c, SUM(x) AS s FROM t GROUP BY k, c) GROUP BY k` is typed. An expression, a bare name two sources could supply, a window and a set operation have no answer and stay open, and other dialects read no type this way (an average of integers is a DECIMAL in MySQL, an average of decimals a DOUBLE in DuckDB). `tests/test_derived_types.py` holds the pairs, and the pairs that must stay unproved (another factor, aggregate, column or filter).

**Filters around a grouped derived table that is joined** (`src/kumo_sql_prover/grouped_source_filters.py`, 2026-11-11). A grouped or `DISTINCT` derived table is one relation to the SMT prover, so a filter has to sit on the same side of it in both queries before the two relations can be matched, and an optimizer moves such filters freely. Two shape rules, both for a select whose sources are joined by inner or cross joins only:

- A condition in `WHERE` or in an inner join's `ON` that reads only group keys of one grouped derived table moves into that table's `WHERE` (`... FROM (SELECT k, c, SUM(x) AS s FROM t GROUP BY k, c) AS d, u WHERE d.k = u.k AND d.c BETWEEN 2 AND 5` filters `t` on `c` instead). It keeps or drops whole groups, so it selects the same rows before the grouping. `_push_filter_into_derived` already did this for a select that reads the derived table alone. The condition may hold only columns, literals, comparisons, `BETWEEN`, `IN` lists, `IS [NOT] NULL` and `AND`/`OR`/`NOT`: nothing that can fail.
- A `k IS NOT NULL` inside a grouped derived table is dropped when the select around it compares that group key (`d.k = u.k`, `d.k > 1`, `d.k IS NOT NULL`) in a condition every row must satisfy: the rows it drops form the group whose key is NULL, and no row of that group survives. The same holds one level further in, when the derived table groups a second derived table by the same value, which is where an optimizer leaves the inferred filter in a decorrelated `> (SELECT AVG(..) FROM (grouped) ..)`.
- A condition the derived table already filters on (compared without identifier quoting, a `BETWEEN` also as its two comparisons) is dropped outside and not added inside a second time. `grouped_join_facts` copies a key's filter to the columns joined to it and compares what is already there the same way, and reads a `BETWEEN` as its two comparisons. Before 2026-11-11 the two rules fed each other: a fact that was already there under quoted names was added again on every pass and moved inside again, which left one side of a pair with repeated conditions the other side did not have (TPC-DS 58 in LOGOS).

Both read only a derived table that computes an aggregate: a `GROUP BY` or `DISTINCT` with none is a duplicate removal that the `DISTINCT` and semi-join rules read their own way, and moving a filter into one first cost a QED proof (`testJoinPushTransitivePredicatesRule2`, found by the comparison against `main`; the pair is over the size the second attempt covers). Neither fires through an outer join, a `LIMIT`, a window, `DISTINCT ON` or an extended grouping. `tests/test_grouped_source_filters.py` holds the rewrites, the conditions that must stay (an aggregate output, an expression, `IS NOT DISTINCT FROM`, `OR .. IS NULL`), pairs that must and must not prove, and a comparison of original and rewritten queries on NULL-heavy DuckDB data.

**A `UNION` of tagged branches that each list a key** (`src/kumo_sql_prover/keyed_union.py`, 2026-11-11). `SELECT product_id, 'store1' AS store, store1 AS price FROM products UNION SELECT product_id, 'store2', store2 FROM products` has nothing to remove when `product_id` is a declared key of `products` and NOT NULL: no branch returns a row twice (two of its rows have different keys) and the tag column keeps the branches apart, so it is a `UNION ALL`. `disjoint_union` read this only for branches of at most one row. A branch qualifies when it reads one base table with no join, grouping, window or `LIMIT` and lists every column of one declared key as plain NOT NULL columns (a key column the `WHERE` clause fixes to a literal counts). Without declared keys nothing fires, so the rule matters to proofs that are given keys and to the [conditional verdict](conditional-equivalence.md), which then names the key: the unpivot pairs of the Singh corpus come back as "equivalent whenever `products(product_id)` is a primary key". `tests/test_keyed_union.py` holds the cases, the ones that must stay (a nullable key, equal tags, a join, half of a composite key) and a DuckDB check that the two forms differ exactly when the key fails.

**A row's key looked up through its own table again** (`src/kumo_sql_prover/self_key_membership.py`, 2026-11-11). `SELECT id, name FROM students WHERE id NOT IN (SELECT s.id FROM students AS s JOIN departments AS d ON s.department_id = d.id)` asks, for each student, whether some student with the same id has a department. When `students.id` is a declared key and NOT NULL, that student is the row itself, so the predicate is `NOT EXISTS (SELECT 1 FROM departments AS d WHERE students.department_id = d.id)`, the form the plain `department_id NOT IN (SELECT id FROM departments)` also takes. The pre-pass rewrites `o.k [NOT] IN (SELECT [DISTINCT] i.k FROM T AS i, rest WHERE .. [GROUP BY i.k])` this way when `o` is a base-table source `T` of the select whose `WHERE` holds the predicate, that select joins its sources by inner or cross joins only, `k` is a one-column declared key of `T` that is NOT NULL and not a floating-point column, and the subquery reads `T` once and other base tables through inner or cross joins with no aggregate, `HAVING`, `LIMIT`, window, nested subquery or reference to the query around it. Without declared keys nothing fires; under the [conditional verdict](conditional-equivalence.md) the students and customers anti-join pairs of the Singh corpus come back as "equivalent whenever `students(id)` is a primary key" with the NOT NULL facts the anti-join itself needs. `tests/test_self_key_membership.py` holds the cases, the ones that must stay (a nullable key, half of a composite key, an outer join on either level, a join condition, the select list) and a DuckDB check over made-up queries that the two forms agree when the key holds and differ on some data when it does not.

**A regrouping that carries `ORDER BY` / `LIMIT`** (`src/kumo_sql_prover/tailed_regroups.py`, 2026-11-11). Calcite writes `COUNT(DISTINCT x)` as two groupings, `SELECT t.a, COUNT(t.x) AS n FROM (SELECT a, x FROM s GROUP BY a, x) AS t GROUP BY t.a`, and the normalizer folds such a regrouping back into one grouped select (`_regroup_distinct`, `_roll_up_aggregate`, `_collapse_aggregate`). Those rules decline a select that sorts or cuts its rows, and a report query nearly always does, so the rewrite of TPC-H 16 stayed two groupings and was never matched with the original. `regroup_under_tail` moves the tail onto a select around the regrouping (`tailed_grouping_sets.isolate_tail`, the step that module already takes for grouping sets), lets one of the folding rules rewrite the regrouping as it always has, and puts the tail back: every sort key was an output column of the regrouping, so it is the value of the output of the same name in the folded select, and a key that was no output is folded with the select and dropped from its outputs again. Nothing is rewritten unless a folding rule fires, and the folded select must be a plain grouped select with the same output names in the same order. `tests/test_tailed_regroups.py` holds the rewrites, the selects left alone, pairs that must and must not prove (a different sort direction or `LIMIT`), and a DuckDB check that compares the rows in order.

**A key-only `GROUP BY` over a join that reads a derived `UNION`** (`src/kumo_sql_prover/union_join_grouping.py`, 2026-11-11). `SELECT c.k, c.a FROM (SELECT x AS id FROM s1 UNION ALL SELECT y AS id FROM s2) AS t, c WHERE c.k = t.id GROUP BY c.k, c.a` has no aggregate and no `HAVING` and outputs its grouping keys, so it returns one row per distinct `(k, a)`: it is `SELECT DISTINCT c.k, c.a FROM ..`, which the prover distributes over the `UNION ALL` and matches with `SELECT .. FROM s1, c .. UNION DISTINCT SELECT .. FROM s2, c ..`, the form an optimizer writes (TPC-DS 54 collects its customers this way). `_group_by_to_distinct` already made this step for a select that reads the union alone; this rule makes it when the union is one of several sources joined by inner or cross joins. A select that outputs only some of its keys (what is left once the query around it reads only `k`) still has one row per distinct `(k, a)` and becomes `SELECT kqg.kq_g0 AS k FROM (SELECT DISTINCT c.k AS kq_g0, c.a AS kq_g1 FROM ..) AS kqg`, which keeps the duplicate `k` values the dropped key leaves; that form is read only when every key is a plain column. Declined: an aggregate or window of the select, `HAVING`, `DISTINCT`, `ORDER BY`, `LIMIT`, `ROLLUP` / `CUBE` / `GROUPING SETS`, a star, a key that is a position, an output that is not a key, an outer join, and a select none of whose sources is a derived set operation. The rule is off in the shape fallback.

**A `LEFT JOIN` from a table to its own groups** (`src/kumo_sql_prover/own_group_joins.py`, 2026-11-11). `SELECT s.employee_id, m.top FROM salaries AS s LEFT JOIN (SELECT company_id, MAX(salary) AS top FROM salaries GROUP BY company_id) AS m ON s.company_id = m.company_id` looks every row up in the groups of its own table. A row with a `company_id` is in the group of that `company_id`, so the lookup always finds exactly that group and the `LEFT` keeps nothing an inner join would drop; people write it either way. The join is made inner when the right side is a derived table over one base table with a plain `GROUP BY` on its columns and no `WHERE`, `HAVING`, `DISTINCT`, `LIMIT` or window (a filter could remove the row's own group), the `ON` is exactly one equality per grouping column with the same column of a source that reads the same base table, that source is the first source or reached by inner or cross joins only, and every grouping column is declared NOT NULL (a row with a NULL there is in the NULL group, but `NULL = NULL` is not true, so `LEFT` pads it and an inner join drops it) and not floating-point. Without NOT NULL facts nothing fires, so the rule matters to proofs that are given constraints and to the [conditional verdict](conditional-equivalence.md), which then names the NOT NULL column as the condition. The rule is off in the shape fallback.

**A self-join that looks for a value on two rows** (`src/kumo_sql_prover/duplicate_self_joins.py`, 2026-11-11). `SELECT DISTINCT a.email FROM person AS a JOIN person AS b ON a.email = b.email AND a.id <> b.id` lists the emails two different people share. `a.id <> b.id` means two different rows only when `id` tells rows apart, so when `id` is a declared one-column key that is NOT NULL the query is `SELECT a.email FROM person AS a WHERE a.email IS NOT NULL GROUP BY a.email HAVING COUNT(*) >= 2`, the form `GROUP BY email HAVING COUNT(email) > 1` also takes: an email is listed exactly when at least two rows carry it. `a.id < b.id` and `a.id > b.id` say the same for this purpose (of two different rows one has the larger key, and the listed columns are equal on both). The rule fires on a `SELECT DISTINCT` with no grouping, window or tail that reads the same base table exactly twice through an inner or cross join, whose `WHERE` and `ON` hold nothing but equalities between the same column of the two rows and `<>`, `<` or `>` comparisons of the key column of the two rows, and that lists exactly the equated columns. A key that can be NULL, a composite key, a floating-point key, any other condition, a third source or an outer join leaves the select as it is. Without declared keys nothing fires; the [conditional verdict](conditional-equivalence.md) names the key. The rule is off in the shape fallback.

**A `HAVING` that counts the rows meeting a condition** (`src/kumo_sql_prover/counted_presence.py`, 2026-11-11). `SELECT s.buyer_id FROM sales AS s JOIN product AS p ON s.product_id = p.product_id GROUP BY s.buyer_id HAVING SUM(CASE WHEN p.name = 'S8' THEN 1 ELSE 0 END) > 0 AND SUM(CASE WHEN p.name = 'iPhone' THEN 1 ELSE 0 END) = 0` lists the buyers with a row where the name is S8 and no row where it is iPhone. It is given the form the same question takes with a filter and a membership test: `SELECT DISTINCT s.buyer_id FROM sales AS s JOIN product AS p ON .. WHERE p.name = 'S8' AND NOT EXISTS (SELECT 1 FROM sales AS s2 JOIN product AS p2 ON .. WHERE p2.name = 'iPhone' AND s2.buyer_id = s.buyer_id)`. `SUM(CASE WHEN c THEN 1 ELSE 0 END)` is the number of rows of the group on which `c` is true and is never NULL, so `> 0` keeps the groups that have such a row and `= 0` those that have none; the first "has a row" condition becomes the filter, every other condition asks for a row of the same group, and `DISTINCT` lists each group once. "The same group" is spelled with `=` on the grouping columns, so each must be a column declared NOT NULL and not floating-point, of a source no outer join pads. The rule fires on a select that groups by plain columns and lists exactly those, whose `HAVING` is a conjunction of such counts compared with 0 or 1 (`> 0`, `>= 1`, `<> 0`, `= 0`, `< 1`, `<= 0`; the count written as `SUM(CASE WHEN c THEN n ELSE 0 END)` with a positive whole `n`, `COUNT(CASE WHEN c THEN x END)`, the same with `IF`, `COUNTIF(c)`, or the flag `MAX(CASE WHEN c THEN 1 ELSE 0 END)` compared with `= 1` or `= 0`), and that reads tables and derived tables under their own names through inner, cross or left joins. A derived table is read as it is and copied whole (the form a left join or a CTE has by then); its output counts as NOT NULL when it is such a column of a select that only joins and filters. Any other `HAVING` condition, `COUNT(DISTINCT ..)`, a `SUM` with no `ELSE 0`, an aggregate in the select list, a subquery or window in the select's own clauses, a volatile call, a derived table with `LIMIT`, `ORDER BY` or `LIMIT` on the select, or a grouping column that can be NULL leaves the select as it is. Without NOT NULL facts nothing fires; the [conditional verdict](conditional-equivalence.md) names the column. The rule is off in the shape fallback.

**Character columns on the BigQuery route** (`string_spelling_rules.bigquery_string_column`, 2026-11-11). BigQuery has one character type. A schema written for another engine may declare `CHAR(2)`, but the column a BigQuery query reads is a STRING, so `CAST(c AS STRING)` is `c` there. A query translated to BigQuery carries that cast wherever the original had `CAST(c AS CHAR(2))` or `CAST(c AS VARCHAR)` (Calcite writes both around `CHAR` columns), and the prover used to fold it only for columns declared `VARCHAR`, `TEXT` or `STRING`. In other dialects a `CHAR` and a `VARCHAR` compare trailing blanks differently and the cast is kept, as before.

**Errors.** BigQuery promises no evaluation order between `WHERE`, `ON` and the select list, so an operation that can fail (`/`, `MOD`, `DIV`, INT64 `+ - *`, negation and `ABS`, `CAST`, a `SUM` overflow) is exposed to every row of its `FROM`; only `CASE`, `IF`, `COALESCE` and `NULLIF` branches and the `SAFE_` functions (`SAFE_DIVIDE`, `SAFE_CAST` and `SAFE_` calls) guard it. A proof is "equivalent on the databases where neither query fails", and `result.errors` compares the two queries' fallible operations:

- `none`: neither query has one; the "runtime errors are not modeled" assumption is dropped.
- `same`: every operation in one is matched by one in the other (the same operation on the same row under a weaker guard); both can fail alike.
- `refines`: every operation of the rewrite is matched in the original, and not the reverse: the rewrite never fails where the original succeeds, and the original can fail where the rewrite returns rows (a `SAFE_` function or a guard added).
- `introduces`: some operation of the rewrite can fail on a database where the original returns rows. The proof is withheld (`not_proven`, with the reason and the verdict in `errors`). The prover only says this when it can show such a database (no uninterpreted function stands in for the failing condition).
- `unknown`: none of the above could be established, for example the failing condition depends on an uninterpreted function; the proof stands under the assumption.

The error assumption in the result says which verdict applies. A site is matched through the same table occurrence maps the bag proof uses, so a rewrite that adds a join can only be `same` or `refines` when every original table maps into it. **Sums over groups** (`src/kumo_sql_prover/smt_group_sums.py`). A `SUM` overflows on a whole group, not on one row, so each `SUM` call is a site described by the rows it adds: the rows of its `FROM` that pass `WHERE` and `ON` and have a non-NULL argument, the `GROUP BY` keys, and the argument. A rewrite's `SUM` is matched with the original's when each of its groups holds exactly the rows, with the same argument values, of one group of the original (a map from the original's table occurrences to the rewrite's, and two checks: where the rewrite takes a row the original takes it with the same key and argument, and a group the rewrite computes at all it computes from every row the original puts in that group). Equal inputs overflow alike whatever order the rows are added in. So moving a `HAVING` on a grouping key into `WHERE` is `refines` (the original also adds up the groups `HAVING` drops), the reverse is `introduces`, a filter respelled, a commuted argument or reordered keys are `same`, and `SUM(DISTINCT x)` is matched only with another `SUM(DISTINCT x)`. A witness for `introduces` is a database of at most three rows of one table on which a group of the rewrite certainly overflows (its exact total leaves INT64, which fails in any order) and no `SUM` of the original can (each group's positive part is at most INT64_MAX and its negative part at least INT64_MIN, so no order of additions overflows); it is built only for an INT64 `SUM` over one base table, with no uninterpreted function in the sum. A `SUM` of a window, or of a relation the prover keeps whole and did not read, is one site for that relation: two queries reading the same relation fail alike, and nothing else is related to it. Everything else is `unknown`: a join in the rewrite's sum (the verdict `refines` or `same` is still found, a witness is not), a FLOAT64 or NUMERIC sum, the sum inside an `AVG` (whether `AVG` of INT64 can overflow is not known), a sum under a `CASE` branch or beside an `EXISTS`, and above all a regrouped sum (a pre-aggregation, a finer or a coarser `GROUP BY`, a redundant key): BigQuery's rule for a sum whose total is in range but whose partial sums are not is *unverified*, so a regrouping is never called the same, a refinement or an introduction. Also unverified: that BigQuery adds up a group that a `HAVING` on its key then drops (an optimizer may move the filter below the aggregation; DuckDB does), that `SUM(DISTINCT)` and a window sum fail on overflow as `SUM` does, and that `AVG` of INT64 can overflow at all. A counterexample database for a refutation must still avoid sums that overflow: a `SUM` of a plain column needs small values (below), any other `SUM` argument withholds the refutation.

**Counterexamples.** A refutation is reported as before, and only when no uninterpreted function is involved. A `SUM` of a plain column no longer withholds it; the database must then hold only small values (at most 2**40 per cell), since a sum of such values cannot overflow.

**Still assumed.** A FLOAT64 column is never NaN (NaN grouping, ordering and `NaN <> NaN` are not modelled), `SUM` and `AVG` do not depend on row order (a FLOAT64 sum does), and result column types are not compared. The first two, and the `exact_arithmetic` assumption (`+ - *` exact, no overflow), are dropped when every column the queries read is declared INT64, NUMERIC, STRING, BOOL or another non-floating type and no expression can produce a FLOAT64 (no decimal or exponent literal, `/`, `AVG`, float cast or unknown function); an overflow is then an error site, reported by the verdict.

**Row order of SUM and AVG** (`src/kumo_sql_prover/float_sum_order.py`). A FLOAT64 sum is not associative, so the same values added in another order can differ in the last digits; this repo's own notes say a FLOAT64 sum has no fixed order in BigQuery, and the GoogleSQL aggregate page was not consulted, so that rule is unverified. The SMT model gives an aggregate one value fixed by its argument, rows and grouping, which is right only if the order cannot matter. For a BigQuery proof the listed assumption is therefore one of three things: *dropped* when every `SUM` in both queries reads an INT64, NUMERIC or BIGNUMERIC expression the compiler can type (a column declared so, arithmetic over those, a cast; a column of a derived table, a `WITH` definition or a `UNION ALL` is followed to where it is defined by `sum_argument_types.py` and counts when every source is a column declared INT64, an integer literal, `COUNT`, a cast to INT64, or `+ - *`, `SUM`, `MIN`, `MAX`, `COALESCE`, `IF` and `CASE` over those; a star, an undeclared table, a name two sources could own or a `/` leaves it unplaced, so that stays) and there is no `AVG`, even if a FLOAT64 column is used elsewhere in the queries; *narrowed* to "an identical FLOAT64 SUM or AVG over the same rows returns the same value on both sides" when each `SUM`/`AVG` that could add FLOAT64 values has an identical partner on the other side, meaning the same call over the same sources, filter, grouping and `WITH` definitions as printed text (case, spacing and comments aside), so both sides add the same rows by the same plan (BigQuery does not promise that one plan returns the same last digits each time either; unverified); and *kept* otherwise, with the words `SUM and AVG are treated as independent of row order`. It is kept for the same values reached by a different plan (a filter written another way, a CTE against a derived table, `UNION ALL` branches swapped, `AVG(f)` against `SUM(f) / COUNT(f)`), for a window `SUM`, for a `SUM` in a possibly correlated subquery, for a `SUM` over a column with no declared type (so exactness is not visible; an identical partner still narrows it), and for every other dialect. A pair that regroups the additions (a sum of partial sums, `SUM(f) + SUM(g)` against `SUM(f + g)`, one-sided pre-aggregation) has no partner for its calls and is not proved at all: the aggregate values stay free. The narrowing never makes a proof the prover could not already make; it only removes the order assumption from the list where nothing about order was used. Tests: `tests/test_float_sum_order.py`, the `float-sum-*` and `int-sum-*` cases of the [numeric traps eval](evals/numeric-traps.md).

**A filter inside a global aggregate** (`src/kumo_sql_prover/smt_global_filters.py`). `SELECT SUM(x) FROM t WHERE c` and `SELECT SUM(IF(c, x, NULL)) FROM t` add up the same values: `SUM`, `MIN`, `MAX`, `AVG`, `COUNT` and `COUNTIF` skip a NULL argument, and a global aggregate returns one row whether or not any row passes. When the usual comparison of two global aggregate blocks fails, each block is respelled with its filter moved into every argument (`COUNT(*)` becomes a count of the rows kept) and compared once more. A grouped block is never respelled (the filter there decides which groups exist), nor one holding another aggregate function or a subquery.

**Halving** (`src/kumo_sql_prover/float_halving.py`). A FLOAT64 product and a quotient are two unrelated functions to the solver, so `x * 0.5` against `x / 2` used to be unknown. For an INT64 or FLOAT64 operand and a decimal literal that is exactly `2**-k` (0.5, 0.25, 0.125, down to `2**-60`), the product is read as the division by `2**k`: both are computed in FLOAT64, a power of two and its reciprocal are exact doubles, and one real number rounds to one double. Any other factor (`x * 0.1` and `x / 10` differ in the last bit), a NUMERIC operand and an operand whose type is not visible are left alone.

Tests of the numeric layer: `tests/test_smt_global_filters.py`, `tests/test_float_halving.py`, `tests/test_sum_argument_types.py`, `tests/test_soundness_smt_literal_coercion.py`, `tests/test_smt_values.py`, `tests/test_smt_numeric.py`, `tests/test_smt_errors.py`, `tests/test_smt_group_sums.py`, `tests/test_soundness_smt_numeric.py` and `tests/test_numeric_traps_bench.py`. How many proofs of the prover evals dropped these labels is counted by the [numeric assumption report](https://github.com/wojoe-444/KumoSQL/blob/master/docs/numeric-assumption-report.md).

### A name that is both a select alias and a column

`SELECT b AS a FROM t QUALIFY RANK() OVER (ORDER BY a) = 1` has two candidates for `a`: the output `b AS a` and the column `t.a`. The engines disagree (BigQuery run on 2026-11-10 with inline values, zero bytes billed; DuckDB 1.5.6 run by `tests/test_soundness_alias_resolution.py`):

| Where the bare name is | BigQuery reads | DuckDB reads |
| --- | --- | --- |
| select list, a window there, `WHERE` | the column | the column |
| a bare `ORDER BY` key | the alias | the alias |
| inside an `ORDER BY` expression (`ORDER BY a + 1`) | the alias | the column |
| a window inside `ORDER BY` | the alias | the column |
| `QUALIFY`: a bare name, a window's argument, `PARTITION BY`, `ORDER BY` | the alias | the column |

Two places read the column on every dialect and proved pairs BigQuery answers differently. The SMT prover's `_split_limit` read `ORDER BY a + 1` (and an `ORDER BY a` whose name was one output's alias and another output's expression) as a sort by `t.a`; it now takes a bare key as the output of that name and refuses an expression that reads a shadowing alias. The algebraic prover moved a `QUALIFY` window into the derived table that computes a select's windows, where a bare name can only be a source column; `src/kumo_sql_prover/clause_alias_reads.py` now runs first. Where the alias is the only reading (BigQuery, or a source with declared columns and none of that name) it replaces the name by the alias's expression, so `QUALIFY RANK() OVER (ORDER BY a) = 1` above is proved equal to the same query with `ORDER BY b`. Where the engine would read the column, or the source's columns are not known, the query is refused (`not_proven`). It also refuses an alias of a volatile value, of a subquery, a window's alias read inside another window, and a name two outputs share. `HAVING` and `GROUP BY` were probed with the same pairs and showed no false proof; they are not covered by this module.

A select-list entry has a name `ORDER BY` can use only when it has an alias or is a bare column (or struct field). sqlglot also reports a name for an unaliased `CAST(b AS STRING)`, namely `b`, and `_split_limit` used that name until 2026-11-10: `SELECT id, CAST(b AS STRING) FROM t ORDER BY b LIMIT 1` was read as a sort by the cast and proved equal to the same query with `ORDER BY 2`. BigQuery, run that day with inline values and zero bytes billed, sorts by the column (9 before 10), not by the string (`'10'` before `'9'`). `_output_name` now gives such an entry no name, so `ORDER BY b` is the column.

### Volatile calls

A function the solver-based provers have no rule for is *uninterpreted*: equal arguments give equal results, so `F(x) = F(x)` is `F(x) IS NOT NULL`. That is false for a call that gives a new value each time, and until 2026-11-11 each prover kept its own short list of such calls, written for BigQuery. A name outside the list was taken as deterministic, so with `dialect="postgres"` the SMT and algebraic provers called `SELECT s1 FROM t1 WHERE nextval('q') = nextval('q')` equivalent to `SELECT s1 FROM t1 WHERE nextval('q') IS NOT NULL`. In PostgreSQL the first returns no row (the sequence advances between the two calls) and the second returns every row. The same held for `clock_timestamp()`, SQLite's `randomblob(4)`, MySQL's `UUID_SHORT()` and `SYSDATE(6)`, Spark's `monotonically_increasing_id()` and `randn()`, Snowflake's `SEQ4()` and Oracle's `SYS_GUID()`. Run on 2026-11-11: PostgreSQL 16.15 returns 0 of 3 rows for the `=` form of `nextval`, `random()` and `gen_random_uuid()` and all 3 for `IS NOT NULL`; DuckDB 1.5.6 does the same for `nextval`, `random()` and `uuid()`, and SQLite 3.53 for `randomblob(4)` and `random()`. `now()` and `date('now')` equal themselves within one statement on all three. The MySQL, Spark, Snowflake, Oracle, SQL Server and ClickHouse entries are from those engines' documentation and were not run.

`src/kumo_sql_prover/volatile_calls.py` is now the one list, for every dialect. It tells two kinds apart:

| Kind | Meaning | Examples |
| --- | --- | --- |
| per call | two evaluations in one statement may differ, or the call has an effect | `RAND()`, `RANDOM()`, `UUID()`, `NEWID()`, `nextval('q')`, `seq.NEXTVAL`, `clock_timestamp()`, MySQL `SYSDATE()`, `randomblob(4)`, `SLEEP(1)`, `GET_LOCK`, `monotonically_increasing_id()`, `SHUFFLE`, Oracle `ROWNUM`, model calls (`AI.GENERATE`, `ML.PREDICT`), `AEAD.ENCRYPT` |
| per statement | one value for the statement, read from the clock, the session, the connection or the server | `NOW()`, `CURRENT_*`, `CURDATE()`, `GETDATE()`, `UNIX_TIMESTAMP()` with no argument, `CONNECTION_ID()`, `LAST_INSERT_ID()`, `USER()`, `VERSION()`, SQLite `date('now')` and `date()`, PostgreSQL `'now'::timestamp`, `age(t)` |

Some entries depend on the arguments or the dialect: `UNIX_TIMESTAMP(d)` and `age(a, b)` are functions of their arguments; a string `'now'`, `'today'`, `'tomorrow'` or `'yesterday'` counts where it is read as a time (a cast, a date function) and, in PostgreSQL, anywhere, because there `ts > 'now'` reads the clock; a bare `USER` is the session user in PostgreSQL and Oracle and a column elsewhere. A name counts in every dialect once it is volatile in one, which can cost a proof and never makes one.

What each prover does with the list:

- **SMT, algebraic and bag (U-expression) provers, and the SQLSolver backend:** a pair that holds a call of either kind is never `proven_equivalent`, also when the two queries are the same text. The clock and the session are not part of the database the proof quantifies over, and the BigQuery `CURRENT_*` functions were already refused this way. A per-call call makes the pair `not_proven`. A per-statement call does too, except where the engine promises one value for the whole statement: there the first three provers can answer `proven_conditionally` (see [calls fixed for the statement](#calls-fixed-for-the-statement-conditional-proofs) below). The check runs twice: where the compiler meets the call, and on the two queries as written after a proof is found (`smt_equivalence.without_volatile_proof`), because a normalization rule may have merged two calls or dropped one before the solver saw them. `WHERE RAND() < 2 OR TRUE` against no filter is true and was proved by the algebraic prover; it is now `not_proven`.
- **Structural prover:** unchanged in principle. A call of either kind is accepted only when left identical and in place; the list now also covers typed nodes it did not (model calls, `'now'` read as a time).
- **Executed comparisons:** `refute.order_dependence` names such a call, so a difference a volatile query shows is not reported as a counterexample.

**Functions the prover does not know.** A call sqlglot has no class for and the list does not name (`my_udf(x)`, `ds.clean(x)`, an engine built-in sqlglot does not model) is still read as a function of its arguments. It may be a user-defined function that is not one. A proof that reads such a call now says so in its assumptions: "functions the prover has no definition for return the same value for the same arguments: MY_UDF". The proof stands only if that holds.

**Limits.** The list is written from the engines' documentation, not derived from them; a volatile built-in missing from it is read as deterministic and shows up only in that assumption line. The many rule modules still carry their own guards (`exp.Rand`, `exp.Anonymous`); the check on the queries as written is what the result rests on.

### Calls fixed for the statement: conditional proofs

A query that filters on `CURRENT_DATE` is not a function of the tables alone, so it is never `proven_equivalent` to anything. What an analyst rewriting such a query needs is weaker: *run at the same statement time, the two queries return the same rows on every database.* Since 2026-11-11 the SMT, algebraic and bag provers answer that as `proven_conditionally`, the verdict [conditional equivalence](conditional-equivalence.md) already uses for facts about the data, with a condition that names the calls:

```text
SELECT a FROM t WHERE d >= CURRENT_DATE() AND a > 1      vs      SELECT a FROM (SELECT * FROM t WHERE a > 1) WHERE d >= CURRENT_DATE()
proven_conditionally: ...; equivalent when both queries run at the same statement time (CURRENT_DATE)
  condition: both queries run at the same statement time, so each of these has one value in both: CURRENT_DATE
```

The verdict is given whether or not `conditional=True` was asked for, because nothing weaker is true of such a pair. `result.proven` stays `False`, the command line exits 3, and no benchmark counts it as a proof.

**How.** Within one statement such a call returns one value however often it is evaluated, so it is a constant the prover knows nothing about. Before the provers see the pair, `kumo_sql_prover.statement_values` replaces each such call with a call to a function with no arguments that the provers have no definition for (`KQ_FIXED_1_CURRENT_DATE()`), the same name for the same call in both queries. The provers already read an unknown function as "equal arguments, equal result", which for no arguments is "one value". Nothing else is assumed about the value: not its type, not that it is non-NULL, not that `CURRENT_DATE` is the date of `CURRENT_TIMESTAMP`. So `WHERE CURRENT_DATE() > DATE '2020-01-01'` is not proved equal to no filter, and `d < CURRENT_DATE()` is not proved equal to `d < CURRENT_DATE('UTC')`. The replacement is made in the text at token positions, so the rest of the query reaches the provers exactly as written, and it is used only when the text then parses to the same tree as the replacement made in the syntax tree.

| What | Which |
| --- | --- |
| Dialects | BigQuery, PostgreSQL, MySQL, DuckDB, Spark, Databricks, Trino, Presto: each documents one value per statement or per transaction. DuckDB 1.5.6 was run (one value for 3,000,000 rows, and for `now()`, `get_current_timestamp()`, `transaction_timestamp()` and `current_timestamp` alike); the others are from the documentation. |
| Clock calls (condition kind `same_statement_time`) | `CURRENT_DATE`, `CURRENT_TIME`, `CURRENT_DATETIME`, `CURRENT_TIMESTAMP`, `NOW()`, `CURDATE()`, `CURTIME()`, `TODAY()`, `LOCALTIME`, `LOCALTIMESTAMP`, `UTC_DATE()`, `UTC_TIME()`, `UTC_TIMESTAMP()`, `STATEMENT_TIMESTAMP()`, `TRANSACTION_TIMESTAMP()`, `GET_CURRENT_TIMESTAMP()`, `GET_CURRENT_TIME()`, `UNIX_TIMESTAMP()` with no argument; a literal argument (`CURRENT_TIMESTAMP(6)`, `CURRENT_DATE('UTC')`) makes a different call |
| Session calls (kind `same_session`) | `CURRENT_USER`, `SESSION_USER`, `SYSTEM_USER`, `USER()`, `CURRENT_SCHEMA`, `CURRENT_DATABASE`, `CURRENT_CATALOG`, `DATABASE()`, `CONNECTION_ID()`, `VERSION()` |
| One value, several spellings | `NOW()`, `TRANSACTION_TIMESTAMP()` and `GET_CURRENT_TIMESTAMP()` are `CURRENT_TIMESTAMP`; sqlglot already reads MySQL `CURDATE()` and DuckDB `today()` as `CURRENT_DATE`. PostgreSQL's `statement_timestamp()` is a different clock from `now()` inside a transaction and is kept apart. |

**What stays `not_proven`.**

- Per-call calls (`RAND()`, `nextval`, `clock_timestamp()`, MySQL `SYSDATE()`, `GENERATE_UUID()`), alone or next to a statement value.
- Other dialects. SQLite promises one value only within one `sqlite3_step`, which is one result row (3.53.1 did keep the value across rows when tried); SQL Server, Oracle, Snowflake and ClickHouse were not checked.
- Spellings whose meaning depends on the reader: a bare `SESSION_USER` or `CURRENT_SCHEMA` that the dialect's parser reads as a column, PostgreSQL's bare `USER`, `'now'::timestamp`, `ts > 'now'`, `date('now')`, `age(t)`; and session state that a statement can change or that describes the last statement (`LAST_INSERT_ID()`, `FOUND_ROWS()`, `ROW_COUNT()`).
- A call the token scan and the parser do not agree on (`SELECT a AS current_date ... WHERE d < current_date`), text with more than one statement, and text that already holds a name starting with `KQ_FIXED_`.
- Refutations. The solver would be free to pick the clock's value, and a replay runs the two queries at two different times, so a difference found for such a pair comes back as `not_proven` with the reason "the queries may differ, but a counterexample is not reported ...". The executed counterexample search already skipped such pairs.

**Limits of the evidence.** The condition is a statement about how the queries are run, so it has no `check_sql`: nothing in the warehouse can be counted to confirm it. Two tables built by two statements at different times do not meet it, even when the model text is the same. The conditional benchmarks cannot hold the clock still between two runs and report such a proof as unchecked. On the benchmark pairs that hold a volatile call (46, found by scanning every re-check adapter in KumoSQL) three became conditional proofs on 2026-11-11 (VeriEQL Calcite pair 394 and two SQLFluff semantic-fix pairs) and none is counted as proved.

Tests: `tests/test_statement_values.py` (rewrites proved under the condition in each dialect by each prover, different reads kept apart, sixteen per-call calls that stay unproven alone, unchanged and next to a statement value, the engines and spellings left out, the text left as written, no counterexample).

Tests for the list: `tests/test_volatile_calls.py` (each listed call per dialect, functions that must not be listed, the reported pairs through the three solver-based provers, calls the rules remove, the assumption line, the structural prover's identical-and-in-place rule).

## Algebraic prover and SQLSolver (no admin rights)

What makes [SQLSolver](https://github.com/SJTU-IPADS/SQLSolver) (SIGMOD 2024) strong is that it treats queries as arithmetic over tuple multiplicities: under bag semantics `UNION ALL` is addition, a join is multiplication, and aggregates over a sum split into partial aggregates combined arithmetically. `kumo_sql_prover.algebraic_equivalence` brings that into KumoSQL in pure Python on top of the existing Z3 prover, so it installs per user with `pip install --user -e ".[smt]"`:

- joins, filters and projections distribute over a derived `UNION ALL`;
- `COUNT`, `SUM`, `MIN` and `MAX` over a `UNION ALL` equal the same function over per-branch partial aggregates (`COUNT` combines with `SUM`), with or without `GROUP BY`;
- redundant regrouping of an already-grouped subquery is dropped, also when an output combines several aggregates (`SUM(total) / SUM(n)` over a finer rollup becomes `SUM(x) / COUNT(x)`, `regroup_arithmetic.py`; `COUNT(a, b)` over a regrouping on extra keys `a, b` is `COUNT(DISTINCT a, b)`, `tuple_count_rules.py`), a constant regrouping (`GROUP BY TRUE`) of a select grouped only by constants reads its one row (`constant_regroup_rules.py`), and union branches are put in a canonical order and naming so equal shapes compare equal.

An integer filter on a projected grouping key is also tested on columns joined to that key by inner equalities of the same declared integer type (`grouped_join_facts.py`). This preserves every joined row and its multiplicity; outer joins, grouping sets, missing types and alias column lists decline.

A complete declared NOT NULL integer key fixed by strict correlation can be exposed in a plain GROUP BY without splitting its groups (`correlated_key_groups.py`). This enables existing singleton-group and guarded lateral-projection readers while preserving empty-input behavior. Global aggregates, floating coercions, outer padding, positional aliases and source modifiers are declined.

The integrated membership rules use one per-proof assumption collector: typed nonnullable ANY, counted nullable membership, passthrough wrappers retain their guards and attach any grouped-equality conditions to the public proof. Boolean classification helpers remain a dependency of typed ANY; the optional numeric-output canonicalizer is not applied globally because it weakened three established projection proofs. A nullable lateral Boolean group is exposed as CASE WHEN EXISTS(rows) THEN TRUE ELSE NULL only under its strict local non-NULL/group-cardinality guards (`lateral_boolean_groups.py`).

Schema facts strengthen proofs: pass `constraints={"orders": TableConstraints(not_null=frozenset({"id"}), keys=(("id",),))}` to `prove_equivalent_smt` or `prove_equivalent_algebraic` and the prover uses NOT NULL columns and keys (a join of a table to itself on its key is dropped, `IS NOT NULL` on a NOT NULL column is redundant), and counterexamples respect them. Blocks that can never return a row are dropped (so `WHERE a = 1 AND a = 2` equals `WHERE 1 = 0`), a global aggregate over no rows is the constant row `COUNT = 0`, others NULL, `compare_names=False` ignores output column names and `dialect="mysql"` reads other dialects. `EXISTS`, `IN`, `NOT IN`, `NOT EXISTS`, `INTERSECT`, `EXCEPT` and `LEFT`/`RIGHT`/`FULL` joins are handled as existence tests and anti-joins: two tests are the same when each implies the other, a required test on a unique key or under `DISTINCT` becomes a join, and an outer join is an inner join plus a NULL-padded no-match branch. A join to a `DISTINCT` or `GROUP BY` derived table on all of its columns is the same existence test (its columns may be NULL until the join pins them, so `WHERE d.x IS NULL` still sees a NULL row), and `HAVING` on group keys is a `WHERE`. A DISTINCT aggregate finished in a second grouping (`SUM(p)` over `GROUP BY k, x` next to `SUM(x)`) is read back as `SUM(DISTINCT x)`, and `MIN(k)`/`SUM(DISTINCT k)` of a group key is the key. `ORDER BY .. LIMIT n [OFFSET m]` (or `ORDER BY .. OFFSET m` alone) at the end of a query is compared by limit, offset and ordering (by output column) with the queries underneath proved equivalent; when the ordering leaves ties, the result's assumptions say rows tied on it must be cut the same way. Cuts inside the query are lifted, merged or dropped only where that holds for every way of breaking ties (see [ORDER BY, LIMIT and OFFSET](evals/sqlsolver.md#order-by-limit-and-offset)). `LIMIT 0` is an empty result, and a `LIMIT` inside a derived table is read as the same relation only when its text matches on both sides (also listed as an assumption). Constant dates are folded (`DATE('1994-09-01 +08')`, `date + INTERVAL 3 MONTH`, `DATE_ADD`) so equal dates compare equal, and string and date ordering uses a one-to-one rank instead of Z3's slow string order. Pre-aggregated tables are unnested (`src/kumo_sql_prover/eager_aggregation.py`): an aggregate over a join with a grouped subquery (`SUM(d.s * w)`, `SUM(d.count)`, `MIN`/`MAX` of its own `MIN`/`MAX`) becomes the flat aggregate, and a join of grouped subqueries read off by arithmetic (`p.sum * q.count`) becomes one aggregate over the flat join; shapes that would change how many times a group is counted are left alone. An aggregate of values that are all NULL is constant (`COUNT(NULL)` is 0, `SUM(NULL)` is NULL, a global one is a single constant row), `UPPER(UPPER(x))` is `UPPER(x)` (not `UPPER(LOWER(x))`: `UPPER(LOWER('İ'))` is `'I'`), `CONCAT` nests flatten, `(a, b) IN (SELECT x, y ...)` is an existence test on every column. An aggregate over an outer join reads the join as one derived relation with positionally named columns (and a derived table that only computes expressions over one table is folded into the query that uses it), so two spellings of the same join compare equal. Column names are case-insensitive, a `UNION ALL` source is read only for the columns the query uses (in any order), the group-key conjuncts of a mixed `HAVING` move to `WHERE`, and a `GROUP BY TRUE` derived table over constants is an existence test. A derived table that only filters or joins (no grouping) under a grouped select is folded into it, `x IS NOT NULL` is dropped when another condition compares `x` or the column is declared NOT NULL (and no outer join can pad it), and `1.00` reads as `1`, so a derived relation written two ways has one identity. A correlated scalar aggregate compared in WHERE (`x < (SELECT 0.2 * AVG(q) FROM t WHERE t.k = outer.k)`, not `COUNT`, equality correlations only) is read as the join with a `GROUP BY k` table, a derived relation is identified by position rather than output name, two derived relations written differently are one relation when the prover shows them equal, and `HAVING MIN(x) IS NOT NULL` is dropped when `x` is never NULL. `a LEFT SEMI JOIN b ON c` is `WHERE EXISTS (SELECT 1 FROM b WHERE c)` (`LEFT ANTI JOIN` is `NOT EXISTS`), `x IN (SELECT k FROM t GROUP BY k HAVING f(agg))` reads the groups as a derived table with the HAVING as a condition on its aggregates, and two existence tests of one query that its plain conditions make equal (`o.k = l.k AND EXISTS(.. o.k) AND EXISTS(.. l.k)`) are one test. Window functions are computed in a derived table over the select's FROM and WHERE (`QUALIFY` becomes a condition on it), which the prover keeps whole: two queries agree when their window computations read alike, and the proof assumes ties in ORDER BY resolve the same way. A window column of a derived table that nothing reads is dropped first (`src/kumo_sql_prover/unread_windows.py`): a window never adds or removes a row. Equal windows are given one spelling first (`src/kumo_sql_prover/window_canonical.py`): the explicit default frame, full frames of SUM/COUNT/MIN/MAX/AVG and ORDER BY keys fixed within a partition are dropped, windows over a grouped derived table are read over the grouping, and unread window columns are pruned. A window's NULLS FIRST or NULLS LAST placement is part of its identity, so windows that differ only there are never proved equal. `AVG(x)` is `SUM(x) / COUNT(x)`, so it equals the spelled-out quotient (and `COUNT(*)` when `x` is never NULL). BigQuery conveniences read as their plain forms: `WITH` tables are inlined, `JOIN .. USING (k)` is `ON a.k = b.k` (the merged column is read from the left side, `SELECT *` lists it first), `* EXCEPT (..)` and `* REPLACE (..)` expand to explicit columns, `COUNTIF(c)` is `COUNT(CASE WHEN c THEN 1 END)` and `SAFE_DIVIDE(a, b)` is `IF(b = 0, NULL, a / b)`; `tests/test_bigquery_refactors.py` lists the everyday refactors proved and the near misses refused. An uncorrelated scalar subquery (`x = (SELECT MAX(r) FROM t)`) that appears on both sides, written the same or provably equivalent, is one shared unknown value (every column in it must bind inside it, otherwise it is left alone; the proof assumes it returns at most one row), `YEAR(d)`/`MONTH`/`DAY` equal `EXTRACT`, `(SELECT 1)` is read as `1`, `IN`/`EXISTS` over a subquery with `WHERE FALSE` (and no aggregate or grand-total grouping such as `GROUP BY ()`, `ROLLUP`, `CUBE` or `GROUPING SETS` listing `()`, which still return their one row) or `LIMIT 0` as FALSE, and `agg(x) FILTER (WHERE c)` as `agg(CASE WHEN c THEN x END)`. With a declared key, a keyed table joined to a pre-aggregated one (`customers JOIN (SELECT customer_id, SUM(x) .. GROUP BY customer_id)`) is the flat aggregate grouped by the key, and `SELECT DISTINCT` over a `UNION ALL` is `UNION DISTINCT` (not when a `LIMIT` or `OFFSET` cuts the whole union). A filter on the right side of a `LEFT JOIN` written as a derived table is the same as in the ON clause, a grouped select over a derived table that only lists a join's columns reads the join itself, and bare columns in a grouped select over an outer join are matched to their source from the schema. A `LEFT JOIN` is read as an inner join when its null-extended rows cannot survive: a WHERE test or later join condition that is never TRUE on NULL (including `IN (subquery)` and a correlated `EXISTS`), a NOT NULL foreign key to the joined columns, or a `HAVING` that drops groups with no match while every aggregate skips the padded rows. A WHERE test of a column that a LEFT JOIN's ON equates to the far side (`WHERE a.k = 2` with `ON a.k = b.k`) is also tested on the far side in the ON. A parenthesized join group (`c LEFT JOIN (a JOIN b ON ..) ON ..`) is read as a derived table; see [join rewrites](evals/join-rewrites.md) for what proves and what does not. With declared column types (`types={'orders': {'amount': 'DECIMAL(15, 2)'}}`, filled from the saved BigQuery catalog's `INTEGER`/`NUMERIC` columns) a `CAST(x AS DECIMAL(p, s))` that keeps every value of `x` is dropped, and a grouped derived table lists its keys and aggregates in a fixed order so two spellings of it read alike. A correlated scalar aggregate in the select list (`(SELECT SUM(y) FROM b WHERE b.id = a.id)`, not `COUNT`) is a left join to the grouped table, a global `SUM`/`MIN`/`MAX` of a grouped select's own `SUM`/`MIN`/`MAX` is the aggregate over all rows, `x IN (SELECT .. UNION ALL SELECT ..)` is an `OR` of the branches (again not under a `LIMIT` or `OFFSET` on the whole union, which would be lost), `WHERE x IS NOT NULL` over a global aggregate of `x` is dropped (`COUNT(*)` becomes `COUNT(x)`), `LOWER(TRIM(x))` is `TRIM(LOWER(x))` `a || b` is `CONCAT(a, b)`, and an `ORDER BY .. LIMIT` derived table that the outer select only projects is the limit at the top. `, UNNEST(arr) [AS t] [WITH OFFSET AS o]` and `CROSS JOIN UNNEST(..)` (not in an outer join) read the array as a table of (array, element, offset) rows with one row per array and offset, so two spellings over the same array compare equal; arrays are known by their text, and no counterexample is generated for a query that unnests. A grouped derived table joined on its key need not repeat an `EXISTS` test that the join already makes on the same key, `EXISTS` filters on a lone-table derived table are tested in the select that joins it, a select that only lists columns of a grouped derived table reads that table (unread outputs of a derived table are dropped, but a global aggregate always keeps one aggregate, since without it the one row becomes a row per input row, and that holds for each branch of a `UNION ALL`; `IN` is not turned into `EXISTS` next to a global aggregate, because a bare column there reads NULL over no rows in SQLite and MySQL), and `IS NOT NULL` on arithmetic over `SUM`/`MIN`/`MAX`/`AVG` of NOT NULL columns is dropped. Counterexamples are not generated for queries with such tests. BigQuery string literals are given one spelling before the provers and the DuckDB re-check read them (`src/kumo_sql_prover/string_literals.py`): sqlglot keeps escapes such as `\"` undecoded, so `'a\"b'` and `'a"b'` looked like different strings, and it reads two adjacent quoted names (`` `col``col` ``) as one name with a backtick in it. Raw strings and strings with `\x`, `\u` or octal escapes are left as written, so those stay unproven rather than wrong. Bytes literals (`rb'..'` too) are decoded and written back with every byte that is not printable ASCII, or is a quote or a backslash, as `\xHH`: sqlglot read `b'\\x41'` (four bytes) and `b'\x41'` (the byte `A`) alike, and the structural prover proved queries using them equal. A `CAST` to a parameterized type (`NUMERIC(10, 2)`, `STRING(5)`), which BigQuery rejects and sqlglot prints without its parameters, is never proven equal to anything. Batch-solved rules (each in its own module): `a DIV b` of non-negative integer literals is folded (`int_div_rules.py`); Calcite's counted-intersection encoding with renamed outputs is read as `INTERSECT` (`intersection_rules.py`); an uncorrelated `EXISTS` in a `LEFT JOIN`'s ON is a filter on the padded side (`outer_join_exists.py`); a `LEFT JOIN` whose padded rows a later outer join's ON always rejects is inner (`outer_on_rejection.py`); a correlated column pinned to an integer constant by a top-level conjunct or a non-padded derived table reads as that constant inside subqueries (`constant_correlation.py`); a pure grouping over an outer join of distinct inputs is the join itself, and an outer join ruled out by an equivalent `NOT EXISTS` is the preserved side padded with NULLs (`grouped_outer_joins.py`). `python tools/sqlsolver_bench.py` measures coverage on SQLSolver's published Calcite, Spark, TPC-H and TPC-C pairs (results in `docs/evals/sqlsolver.md`); every proof is re-run on random DuckDB databases. `python tools/rbot_bench.py` does the same for the Calcite rewrite pairs shipped with [R-Bot](https://github.com/curtis-sun/LLM4Rewrite) (Apache-2.0). `python tools/calcite_mined_bench.py` scores pairs mined from Calcite's current rule tests (`tools/calcite_plan_to_sql.py`). `python tools/cosette_bench.py` scores the examples of [Cosette](https://github.com/uwdb/Cosette) (BSD-2-Clause) and the [SPES](https://github.com/georgia-tech-db/spes) Calcite pairs (Apache-2.0) worded differently from SQLSolver's. `python tools/qed_bench.py` scores the Calcite cases of the [QED prover](https://github.com/qed-solver/prover) (MIT), converted from QED's relational-algebra JSON to SQL by `tools/qed_to_sql.py`. A `GROUP BY` or `DISTINCT` over one table that includes a NOT NULL key (or one fixed by `WHERE k = 10`) reads each row's own values, and `EXISTS` over a global aggregate is TRUE.

**Aggregate facts.** Aggregate values are free in the SMT model, so the prover states what every group satisfies (`src/kumo_sql_prover/smt_equivalence.py`, `_aggregate_facts`): `COUNT` and `COUNTIF` are whole numbers of at least zero (so `COUNT(x) > 1` is `COUNT(x) >= 2`) and a group has at least one row; the group's representative row is one of its members, so a non-NULL argument there makes `SUM`/`MIN`/`MAX` non-NULL and `COUNT` at least one; an argument fixed by the group key is its own `MIN`/`MAX`/`SUM(DISTINCT)`/`BIT_AND`/`BIT_OR`, `COUNT` of it is 0 for a NULL key and `COUNT(*)` otherwise, and `COUNT(DISTINCT)` of it is 0 or 1; `SUM`/`MIN`/`MAX` of `x` is NULL exactly when `COUNT` of an argument NULL on the same rows is 0; and `COUNT(a)` equals `COUNT(b)` when `a` and `b` are NULL on the same rows. `COUNT(a, b)` counts the rows where no argument is NULL and `COUNT(DISTINCT a, b)` the distinct such tuples; the tuple's value is an uninterpreted function of its components. `BIT_AND`, `BIT_OR` and `BIT_XOR` are uninterpreted aggregates (the first two ignore duplicates); their value over no rows differs by engine, so an empty one is never folded to NULL. A row joined back to a `GROUP BY` derived table of its own table (no `WHERE`) on the group key is a member of that group, so a non-NULL value makes the group's `MAX` non-NULL and at least that value (`MIN` at most), which proves `CASE` arms that differ only when the group's `MAX` is NULL. A `GROUP BY` whose outputs fix its keys returns a set, and a `SELECT DISTINCT` compares with a `GROUP BY` as the grouping on its outputs. In the expressions themselves, `x * 1` is `x` for an integer `1` (or an exact decimal one; not `1e0` or BigQuery's `1.0`, which are `FLOAT64` and round an INT64 `x` past 2^53), a `CASE`, `IF`, `COALESCE`, `NULLIF` or set operation with a visibly `FLOAT64` branch (a `FLOAT64` literal or cast, or arithmetic over one) reads each other non-literal branch as `CAST(.. AS FLOAT64)` (the common type; a column declared `FLOAT64` in `types` counts as visible, and values from different undeclared columns are combined as they are, adding the assumption that they have the same numeric type), a comparison (`=`, `<`, `IN`, `BETWEEN`, a simple `CASE`) of an INT64 or NUMERIC value with a `FLOAT64` one reads the first the same way, so `a = b AND b = c` over INT64 `a`, `c` and `FLOAT64` `b` does not give `a = c` (2^53 and 2^53 + 1 both equal 2^53 as `FLOAT64`; a `FLOAT64` literal below 2^53 converts nothing, and comparisons of undeclared columns carry the same assumption), literal arithmetic is computed where the engine computes it exactly (integers everywhere, decimals in MySQL, Postgres and DuckDB but not BigQuery, whose decimal literals are `FLOAT64`, and exponent literals only in Postgres; so BigQuery's `0.1 + 0.2 = 0.3` is never proven TRUE, while with `exact_arithmetic` it is, under that assumption), a decimal or exponent literal is modeled as its exact value only with at most 15 significant digits inside the normal `FLOAT64` range (`1e-324` and `2e-324` are both 0, `1e400` overflows; such literals are not modeled), `ROUND(x, 0)` is `ROUND(x)`, a cast of a value already cast to the same type is that cast, an integer division cast to an integer type is the division, and `ROUND`, `ABS`, `FLOOR`, `CEIL`, `SQRT`, `LN`, `EXP`, `UPPER` and `LOWER` return NULL for a NULL argument. **Set-reading aggregates** (`src/kumo_sql_prover/set_aggregates.py`): `MIN`, `MAX`, `BIT_AND`, `BIT_OR`, `LOGICAL_AND`, `LOGICAL_OR` and every `DISTINCT` aggregate depend only on the set of non-NULL values of their argument, so two global aggregates (no `GROUP BY`) that call the same such function at each position are equal when `SELECT DISTINCT arg ... WHERE arg IS NOT NULL` is the same set on both sides; a plain `SUM`/`COUNT`/`AVG` qualifies when it reads the only column of a derived table that never repeats a row. This proves `MAX(num)` over `GROUP BY num HAVING COUNT(num) = 1` equal to the same with `COUNT(*) = 1` (the second keeps a NULL group that `MAX` ignores). A key-only filter also moves into a grouped derived table that has a `HAVING`, and an outer `SELECT DISTINCT` drops the deduplication of its derived source.

A `SELECT DISTINCT` derived table joined to keyed tables on declared integer columns is lifted to the outer select (`src/kumo_sql_prover/keyed_set_join.py`): when conjunctive equalities between declared integer columns fix a complete NOT NULL key of every joined table, and the outer projection determines each distinct tuple, the outer rows are already unique, so the inner `DISTINCT` moves out as an outer one without changing the bag. It declines on GROUP BY, HAVING, windows, ORDER BY, LIMIT, outer joins, non-integer or undeclared types, and any modifier on the derived table, so a rewrite is never applied where an equality could coerce or collapse values. Measured on master 884470c it proves Cosette's `ex1sigmod92`, `ex2sigmod92` and `ex2sigmod92simpl` (Cosette 56/59 to 59/59, 0 wrong; the rule was written with those pairs in view, tuned on test; it comes from a patch by an outside reviewer, narrowed to exact integer types in review). `tests/test_keyed_set_join.py` holds the near misses, each with a DuckDB witness.

A query split into partitions by a filter is put back together (`src/kumo_sql_prover/partition_rules.py`): `UNION ALL` branches that are the same query except for WHERE filters no row can make TRUE twice are one branch filtered by their `OR`, dropped when the `OR` is always TRUE (`p`, `NOT p`, `p IS NULL` under three-valued logic, as in SQLancer's TLP), and a global `SUM` of `COUNT`s, `SUM` of `SUM`s, `MIN` of `MIN`s or `MAX` of `MAX`es over a `UNION ALL` of global aggregates is one aggregate over the `UNION ALL` of their arguments. See [docs/evals/fuzzing.md](evals/fuzzing.md#partition-recombination).

Under `SELECT DISTINCT`, where duplicates cannot show, a query splits into a union of simpler ones (`src/kumo_sql_prover/set_split_rules.py`): a join on a `CASE WHEN a = 1 THEN b WHEN b = 1 THEN a END` key becomes one branch per arm (a later arm skips rows an earlier arm took, unless both conditions force the same value), a filter `CASE .. END = x` becomes an `OR` of the arms, a derived `UNION` or `UNION ALL` joined in distributes into a `UNION` of copies, and `x IN (SELECT c FROM (p UNION q) d WHERE w)` is an `OR` of one test per branch. The prover then compares the sets branch by branch, splitting a branch on an `OR` in its filter when no single branch on the other side contains it (so `p.a BETWEEN q.a AND q.b OR q.a BETWEEN p.a AND p.b` over a self-join matches one direction with the aliases swapped; no check is made twice, and a piece of the other side that only adds a filter to a branch already refuted for the case is skipped), reads a `DISTINCT` derived table inside a plain `SELECT DISTINCT` as the rows it deduplicates when it is not joined on all of its columns, and knows that a row the query reads witnesses an `IN`/`EXISTS` test over its own table (`l.u = 1 AND l.p NOT IN (SELECT p FROM l WHERE u = 1)` is never TRUE). Own table means every qualifier matches: `s1.l` is no witness for `s2.l` or a bare `l`, and BigQuery dataset and table names compare case-sensitively. `tests/test_set_split_rules.py` pins the near misses each step must refuse. A filter `x <> y` splits the same way into `x < y` and `y < x`. `ABS(x - y)` keeps `-` and `ABS` uninterpreted but states what holds for every number type (IEEE subtraction gives exactly `-(y - x)` and is zero only when `x = y`): it is `ABS(y - x)`, it is `x - y` when `y < x` and `y - x` when `x < y`, and it is 0 when `x = y` and positive otherwise. So `MIN(ABS(a.x - b.x)) ... WHERE a.x <> b.x` over a self-join equals `MIN(p2.x - p1.x) ... ON p1.x < p2.x`. This reads `x` and `y` as numbers (MySQL also subtracts strings, which sort differently), and the proof lists that assumption; with exact arithmetic, `ABS` is the absolute value. `tests/test_abs_difference.py` holds the near misses.

`AVG`, `DISTINCT`, outer joins, `LIMIT` and `UNION DISTINCT` are left alone. [`tests/test_algebraic_equivalence.py`](../tests/test_algebraic_equivalence.py) runs every rewrite on random SQLite databases (empty tables and NULLs included) to check normalization never changes results.

Aggregate queries written in different shapes are brought to one form (`src/kumo_sql_prover/aggregate_rules.py`). A global aggregate whose every aggregate filters with the same `CASE WHEN p THEN x END` is the aggregate of `x` under `WHERE p` (a `GROUP BY` would lose emptied groups and `COUNT(*)` counts every row, so neither qualifies), a global aggregate over `WHERE FALSE` is its constant row and one with no `FROM` reads one row. Under `GROUP BY`, `MIN`/`MAX` of a deterministic expression of the keys is the expression and `COUNT(DISTINCT key)` is 1 (0 for the NULL group), `COUNT(x)` is `COUNT(*)` when `WHERE` compares `x`, `HAVING COUNT(*) >= 1` is dropped, `HAVING SUM(CASE WHEN p THEN 1 ELSE 0 END) >= 1` over a select of keys only is `WHERE p`, and `COALESCE(SUM(c), 0)` of per-branch `COUNT`s is `SUM(c)`. A filter on a grouped derived table's aggregate output is its `HAVING`; `f(MAX(x)) AS v` in an inner-joined grouped derived table is computed outside it as `f(d.m)` (not inside `IN` or `EXISTS`); copies of one grouped query joined `ON` every key with `<=>` (or `ON TRUE` with no keys) are one grouped query; a projection over a join of grouped subqueries reads the join directly; and expressions over `SUM`/`COUNT`/`MIN`/`MAX` and `BOOL_AND`/`BOOL_OR` are split per branch of a `UNION ALL` like plain aggregates (a filter over a `UNION ALL` whose branches aggregate is pushed into each branch).

**What a proof found after normalization discloses** (`src/kumo_sql_prover/normalized_disclosure.py`). The algebraic prover hands the solver the two *normalized* queries, and two things the solver then reports were read off that text, not off the queries as written. A rule that keeps the rows can change which operations fail: `HAVING y > 0` moved into `WHERE` no longer adds up the groups the filter drops, so the solver compared two `WHERE` queries and reported "both queries can raise the same runtime errors" for a pair where one side overflows and the other returns rows. And a sum of partial sums merged into one `SUM` has an identical partner only after normalization, so the narrowed "an identical SUM over the same rows" label was listed for two queries that add in different groupings. Now the error comparison is kept only when the solver itself proves each written query equal to its normalized form with the same error exposure (verdict `none` or `same`; skipped past 6,000 characters, with a two-second limit); otherwise the verdict is `unknown` and the result lists the plain "runtime errors are not modeled" label. The narrowed sum label is kept only when the queries as written pair their `SUM` and `AVG` calls identically; otherwise the row-order assumption is listed again. Neither changes a verdict: the proof stands, what it claims beyond the rows is cut back to what was checked. One known gap stays: a FLOAT64 sum of partial sums against the single sum is still proved, with the row-order assumption listed.

Two small rules run with the shape rules. `x LIKE 'abc'` with no `%`, `_` or backslash and no `ESCAPE` is `x = 'abc'` (`literal_like.py`): always in BigQuery and DuckDB, and in PostgreSQL only when `x` is a base-table column declared VARCHAR or TEXT (a `CHAR(n)` column pads, and `=` and `LIKE` treat the padding differently); never for `ILIKE`, MySQL or SQLite, whose `LIKE` ignores case. An `OR` of `EXISTS` subqueries over the same `FROM` is one `EXISTS` with the filters joined by `OR`, and an `AND` of `NOT EXISTS` likewise (`exists_disjunction.py`); the subqueries must read the same sources as printed and have no `GROUP BY`, `HAVING`, `LIMIT`, `DISTINCT`, aggregate or window, where the row test is not simply "some row passes the filter".

**Declined, never guessed.** A construct the provers cannot read faithfully makes the result `not_proven`, never a proof:

- Rewritten queries pass between the provers as text, and some sqlglot generators change meaning when they print (MySQL writes `a DIV b` as `CAST(a / b AS SIGNED)`, which rounds where `DIV` truncates, `CAST(x AS BOOLEAN)` as an integer cast, and `FULL JOIN` as a `LEFT`/`RIGHT` union that is wrong under an aggregate). `kumo_sql_prover.ast_utils.faithful_sql` prints a query, parses it back and compares the two trees; when no spelling reads back the same, the pair is declined. One spelling is tried for a case BigQuery's writer creates itself: in a select with `ORDER BY`, it prints a `GROUP BY` key that repeats an aliased output as the alias (`GROUP BY CAST(x / 50 AS INT64)` as `GROUP BY segment`), which is another tree and, where the source has a column of that name, another query. When no other spelling reads back, such keys are printed in parentheses, which stops the replacement and changes nothing else (2026-11-11). A parser error of any kind while reading a spelling back, including the compiled parser's `TypeError` for a string where a name belongs, only rules that spelling out.
- A derived table the SMT prover keeps whole (a grouped or `DISTINCT` body it does not read row by row) is one unknown relation per text, and two differently written bodies are proved equal by the prover itself so that they can share one (`smt_equivalence._unify_opaque`). That nested proof reads both bodies in the dialect of the proof it belongs to, handed over through `faithful_sql`. Until 2026-11-10 it read them as BigQuery whatever dialect the caller named, which went wrong both ways under MySQL, PostgreSQL and DuckDB. A proof was lost: `SUM(p * (1 - d))` against `SUM(p * (1.00 - d))` inside a grouped derived table, because `1.00` is an exact decimal there and a FLOAT64 in BigQuery (SQLSolver's TPC-H pair 20, see [the eval page](evals/sqlsolver.md#benchmark-coverage)). And a pair that differs was proved: a body filtering on `x = 0.1` against one filtering on `x = 0.10000000000000000001` over a `DECIMAL(30, 25)` column, one FLOAT64 in BigQuery and two different decimals elsewhere; a row whose `x` is exactly 0.1 separates them. A body with no faithful spelling in its dialect is matched by its text alone and never re-proved. `tests/test_nested_proof_dialect.py` keeps both witnesses for both provers.
- Text or a schema that cannot be read is an answer, never an exception. Fuzzing the entry points (2026-11-10) found inputs that escaped as raw errors: some fifty nested parentheses (sqlglot's parser recurses about twenty frames per level, so the interpreter's stack ends; the BigQuery parser now raises `bigquery_syntax.TooDeeplyNested`, a `ParseError`, for every caller), a chain of 142 `UNION ALL` branches in the executed check, an unclosed quote (a `TokenError`, where only `ParseError` was caught), `t..u` (sqlglot leaves an empty string where a name belongs; `check_modeled` declines it), the number `1e`, an unterminated SQLX `config {` block, and a schema DuckDB cannot hold (a table with no columns, or two tables whose names differ only by case, which are two tables in BigQuery and one name in DuckDB). The provers answer `not_proven`, the bounded check `unknown`, `check_result_equivalence` `error`, the tie analysis an `unsupported` report and the tie-witness search `None`. `tests/test_odd_input.py` runs every case through every entry point in four dialects.
- Text that would end the process, or never finish, is refused when it is read, in every dialect (`bigquery_syntax.read_within_limits`, behind every `sqlglot.parse`, `parse_one` and `Dialect.parse_into` once this package is imported). The refusal is a `TooDeeplyNested`, a `ParseError`, so every entry point answers as it does for other unreadable text. Found 2026-11-10 with the compiled sqlglot build (`sqlglotc`), which routine runs use:
  - **Depth ends the process.** sqlglot's parser and its SQL writer recurse once per level. Pure-Python sqlglot stops at the interpreter's limit (the `RecursionError` above); the compiled build has no such check, overflows the C stack and the process dies with a segmentation fault. On a 512 KB stack that took 400 nested parentheses, subqueries or `CASE`s, 400 of `@`, `ANY` or `INTERVAL` in a row, 3,200 subscripts (`a[0][0]..`), or, while writing a tree that had been read without trouble, 300 JSON steps (`a->'k'->'k'..`) or lambdas; an 8 MB stack took 10,000 nested parentheses. Three limits, the same on both builds: at most `MAX_NESTING` = 100 brackets, `CASE`s, `ARRAY<` types and prefix operators inside each other, counted in the tokens before the parser sees them; a statement whose tokens could take the parser deeper than 80 levels some other way is read on a thread with a stack sized for it (4 KB per token, three times the worst measured use); and the tree that comes back may be at most `MAX_TREE_DEPTH` = 200 nodes deep. A chain of `+ - * / ||`, `AND`/`OR` or set operations is read and written in a loop and counts as one level, so these limits do not refuse a sum of 3,000 columns, 3,000 conditions or 1,000 `UNION ALL` branches.
  - **Calls of a type's name inside each other double the time.** sqlglot reads the inside of `DATE(..)`, `STRING(..)`, `STRUCT(..)`, `TIMESTAMP(..)` or any other call of a type's name twice, once as a type's parameters and once as arguments. Sixteen inside each other take half a second, twenty-four take ninety seconds, forty do not finish. More than `MAX_TYPE_CALLS` = 10 are refused. Next to each other they cost nothing.
  - **Joins with no condition double the time and the memory.** After a join with no `ON` or `USING` (and not `CROSS` or `NATURAL`) sqlglot tries the joins that follow as nested inside it, and reads them again when no `ON` follows. Twenty `JOIN t` in a row took six seconds and 1.1 GB with the compiled build; twenty-four need more than 16 GB. More than `MAX_OPEN_JOINS` = 10 joins waiting for their `ON` are refused, which also refuses eleven nested joins whose `ON`s all come last.

  How a statement is weighed (`bigquery_syntax.nesting_weight`): a parser goes a level deeper only by reading a token, and a comma ends whatever was begun since the last comma at its bracket level. So the weight is the largest number of tokens that can be open at once: for each open bracket, `CASE` or `ARRAY<`, the tokens read directly inside it since its last comma. A select list of 400 expressions weighs a dozen; a `WHERE` of sixty conditions with no comma weighs 245 and is read on the thread. Weighing costs about 0.13 microseconds a token (7% of the compiled parse of a 1,200-token statement); the thread costs a third of a millisecond, which is why only heavy statements get one.

  Evidence and limits. 113 constructs (prefix, infix and postfix operators, calls, brackets, statement forms and comma lists) were read and written in BigQuery, DuckDB, PostgreSQL and Snowflake at 78, 190 and 20,000 repetitions on a 1 MB thread stack, each in its own process: none ended the process. 1 MB is the floor: it is the smallest stack a CPython thread gets unasked, and pure-Python sqlglot itself overflows a 512 KB stack while writing a tree 190 deep. The limits bound what is read from text; a tree built in code can be deeper than any of them, and the compiled writer will then end the process as before. The weight is a bound on sqlglot's grammar as measured, not a proof about every dialect's parser. Two slow readings are left as they are: a chain of pipe `|> SELECT` operators is quadratic (400 take four seconds) and DuckDB reads a chain of subscripts in quadratic time (which the subscript limit caps at a third of a second). `tests/test_odd_input.py` holds the cases, including a process of its own that reads and writes each of them on a 1 MB stack.
- `GROUP BY ALL` is spelled out as the keys it infers (the select items that reference a column and hold no aggregate, as positions) before any prover reads it; with no keys an aggregate-only select is the global aggregate, one row even on empty input. A select of only constants (DuckDB groups by them, BigQuery does not), a star, a window or subquery in the select list, an unknown function (it may be an aggregate) or a `GROUP BY ALL` that may read outer columns is declined.
- A column list on a table alias (`FROM dept AS d(name, x)`, on a table, CTE or derived table) renames by position and is spelled out as explicit renames before proving; a list that cannot be resolved (unknown table, star select, too many names) is declined.
- `IS [NOT] DISTINCT FROM` next to another comparison without parentheses (`a = b IS NOT DISTINCT FROM c`, `a IS DISTINCT FROM b = c`, also beside `LIKE`, `IN`, `BETWEEN` or another `IS`) is declined: sqlglot binds it tighter than `=`, while DuckDB and PostgreSQL read `(a = b) IS NOT DISTINCT FROM c` and `a IS DISTINCT FROM (b = c)`. With parentheses (`a = (b IS NOT DISTINCT FROM c)`) it is proved as usual.
- A text sqlglot reads differently from the engine is declined by every prover entry point. `kumo_sql_prover.parse_check` reads the text a second time with the engine's own precedence (BigQuery, MySQL, PostgreSQL and DuckDB tables) and refuses the proof, with the reason "parser disagreement", when the groupings differ: `a | b & c` against `(a | b) & c` in BigQuery, `a = b < c` and `!a = b` in MySQL, `~1 + 1` and `a = b IS NULL` in DuckDB, or a comparison BigQuery rejects (`a > 10 IS TRUE`). A construct the reader does not know is left to sqlglot, never declined. See [parser checks](parser-checks.md).
- A derived table folded into the query that reads it keeps its output names, and a rewrite that would rename a derived table's outputs is not applied.
- On the NULL-padded side of an outer join only expressions that are NULL whenever their columns are (columns, arithmetic, comparisons, a `CASE`/`IF`/`COALESCE` whose every result is such an expression) are folded into the outer query; constants, `IS NULL` and the like stay in the derived table.
- `GROUP BY 2` and `ORDER BY 2` are spelled out as the second output's expression first, so a constant folded into those clauses later is not read back as a column position.
- A select-list `x IN (SELECT y FROM t ...)` rewritten as `EXISTS (... AND y = x)` qualifies `x` by its outer table, and a subquery table of the same name gets a fresh alias, so the inner scope cannot capture `x` (`deptno IN (SELECT deptno FROM emp ...)` over `emp` is not `deptno = deptno`); when the owner of `x` is unclear the rewrite is skipped.
- Before any rewrite, a bare column in a select with several sources is written with its source's name, so reading a derived table as its base table (which brings that table's other columns into scope) cannot capture it or make it ambiguous.
- The same goes for a bare column a subquery reads from an enclosing query (`EXISTS (SELECT 1 FROM (SELECT 2 * deptno AS f FROM dept) AS t WHERE deptno = t.f)`): when a derived table on the way reads a table with a column of that name, the column is written with its enclosing source's name first; if a source on the way reuses that name, the query is declined.
- A table function handed a CTE by name (DuckDB's `histogram_values(cte, l)`, BigQuery's `TABLE cte`) is declined by every prover, since such a read is not a table reference and the CTE would look unused.
- `DISTINCT` removes repeated output rows, not the repeats an aggregate reads: `SELECT DISTINCT COUNT(*)` over a derived `DISTINCT`, an unread outer join or a join read as `EXISTS` keeps them, so those rewrites apply only when every aggregate is `MIN`, `MAX` or a `DISTINCT` one.
- A `GROUP BY` key the select does not output still splits groups (`SELECT k, SUM(x) .. GROUP BY k, j`): flattening or pulling up such a grouped table is declined, and splitting its aggregate over `UNION ALL` branches carries the hidden key.
- `CASE` results compared with a literal fold only when exact and `FLOAT64` comparison agree, so `2^53 + 1` is never equal to `2^53`.
- A `HAVING` existence test moves into `WHERE` only when `ORDER BY` reads no aggregate, since an ordered `LIMIT` would then pick other groups.
- `ROLLUP`, `CUBE`, `GROUPING SETS` and the empty grouping `GROUP BY ()` are recognized wherever sqlglot keeps them (`kumo_sql_prover.ast_utils.extended_grouping`), so rules that assume one row per group of real input rows decline them: their grand-total group exists even over no rows, so `WHERE FALSE` does not make the select empty. This matters for a list the normalizer does not spell out as a `UNION ALL` (one that repeats a set, like `GROUPING SETS ((x), (), ())`): a key-only grouping, a dropped NULL key or a `COALESCE(SUM(..), 0)` does not simplify there. A `DISTINCT ON` derived table is not a set either (two kept rows can be equal). [`tests/test_soundness_grouping_guards.py`](https://github.com/wojoe-444/KumoSQL/blob/master/tests/test_soundness_grouping_guards.py) keeps these cases.
- Without a schema, a derived table (`(SELECT k FROM u) AS d`, or one that computes `k + 1 AS k1`) is not read as its base table while a bare column in its scope or its subqueries names something it does not output: `u` may have that column and capture a reference that read the outer query (`EXISTS (SELECT 1 FROM (SELECT k FROM u) AS d WHERE x = 2)`). With the table's columns in the schema, only names the table has stop it.
- Names follow lexical scope: a CTE reference reads the nearest `WITH` that defines the name (an inner `WITH q` hides an outer one, also for a column list `q AS d(a)`), and `UNNEST(..) AS a` names its element `a`, which hides an outer alias `a`; a field `a.x` of such an element is declined.
- A set operation converts every branch to the outputs' common type before it compares rows, and the algebraic rules move filters and projections into the branches as if it did not. With `types`, a query in which two branches give one output different known types (declared column types, casts and literals, followed through derived tables and CTEs; an integer literal below 2**53 fits any number type) is declined: over `a.x BIGINT` and `b.x VARCHAR`, `WHERE x = '01'` on the union is not the same filter in each branch (`set_operation_types.py`) Without types, DuckDB and MySQL convert silently, so a proof through a set operation whose branch types are not all known carries the assumption "the branches of each set operation give each output the same type".
- Lifting a cut out of a projection (`limit_rules._lift_cut`: `SELECT f(d.c) FROM (SELECT g AS c FROM t ORDER BY o LIMIT n) AS d` becomes `SELECT f(g) FROM t ORDER BY o LIMIT n`) declines in three cases, each a wrong proof on master. A nested query in the projection (`d.b + (SELECT MAX(b) FROM u)`) declines, because that `b` is `u.b`, and spelling `d.b` as the value `a` turned it into `u.a`. A select-list value that is different each time it is evaluated (`RAND()`, `UUID()`, a clock) declines, because a value read twice would be drawn twice. And a `GROUP BY 2` or `ORDER BY 2` ordinal declines when the new select list puts another item at position 2 (`rebinds_grouping_names`, also used by the grouping rules in `algebraic_equivalence`). `tests/test_limit_rules.py` keeps each witness with the DuckDB database that separates the pair, next to a near miss that still lifts.
- `UNION ALL BY NAME` reorders a branch's select list to match the outputs by name; a branch with an `ORDER BY 1` or `GROUP BY 1` is wrapped and selected from by name instead, so the ordinal keeps its column.
- A single-quoted string or bytes literal holding a line break is not valid GoogleSQL, though sqlglot reads it: in the BigQuery dialect `prove_equivalent` and `prove_equivalent_algebraic` decline such a query rather than prove it equal to the escaped spelling `b'a\x0Ab'`.
- A string compared with a number is not decided by kind (`kumo_sql_prover.string_number_compare`). The provers read a number, a string and a Boolean as different kinds of value and called them unequal, so `WHERE '2' <> 2` was proven equal to the query without the filter. No engine reads it that way: MySQL compares a string with a number as numbers (`'2' = 2` is true, `'abc' = 0` is true), DuckDB and PostgreSQL cast the string to the number's type (an error when it does not parse), and BigQuery rejects the comparison as a type error. A plain comparison (`=`, `<>`, ordering) of a string literal with a number literal that is not an exact small integer on MySQL, DuckDB or PostgreSQL (and any such comparison on BigQuery), arithmetic, a numeric `CAST`, a `COUNT` or a column declared numeric in `types` (or a number with a column declared as a string) is read by the SMT prover as an unknown function of the two values (`converted_eq`, `converted_lt`): a pair that makes the same comparison on both sides can still be proven (a semijoin turned into a join over `sal + 1 = job`), the witness cannot, and a model of the unknown conversion is never reported as a counterexample. The same comparison inside `BETWEEN`, an `IN` list, a simple `CASE` operand or `NULLIF` is declined, as is one column compared with a string literal in one place and a number literal in another (`a = 'abc' AND a = 0` returns the row `a = 0` on MySQL for an integer column). Where the string is an exact small integer the comparison is no longer left unknown on MySQL, DuckDB and PostgreSQL (`kumo_sql_prover.string_number_literals`, applied by both provers before anything else): `'2' = 2` is `TRUE`, `'2' < 3` is `TRUE`, and a column declared as an integer type in `types` compared with such a string (`t.n = '2'`, `t.n < '10'`, `BETWEEN '1' AND '3'`, an `IN` list of such strings and numbers) is compared with the number instead. A small integer is a minus sign and one to nine digits without a leading zero, so no engine reads it through a float or differently from another. Strings with a decimal point, spaces, a sign or a leading zero, decimal and float columns, columns with no declared type, `<=>`, and the dialects BigQuery (a type error there) and the rest are left as written and declined as before. `tests/test_string_number_inference.py` replays the rewrite on DuckDB (rows identical to the original on every operator) and it was also compared with MySQL 8.0 on 530 query shapes with no difference.
- Shapes that other engines' own tests and translations use (2026-11-11, all shape rules, see below): inline rows written as `UNNEST([STRUCT(..), ..])` are read as a derived table (`inline_rows.py`); a query that reads no table is replaced by its rows, worked out by a small interpreter that declines whatever it does not cover (`closed_queries.py`); `COUNT(*)` over a `FULL JOIN` is the count of its `LEFT JOIN` and unmatched `RIGHT JOIN` halves (`counted_joins.py`); `(SELECT COUNT(*) ..) > 0` is `EXISTS` (`count_exists_rules.py`); a subquery test beside a narrower or wider copy of itself keeps one of the two (`subquery_absorption.py`); with declared types a DATE plus a whole-day interval in a comparison is `DATE_ADD` and an equal integer addend on both sides is dropped (`typed_comparisons.py`); in SQLite the digits of `STRFTIME('%Y', x)` compare the same as text and as `CAST(.. AS INTEGER)` (`sqlite_date_text.py`). What each reads and declines is in its module's docstring; the pairs they opened are in [evals/engine-paired-tests.md](evals/engine-paired-tests.md) and [evals/dlbench.md](evals/dlbench.md).

Kinds are also inferred from the query (issue #613), since the SMT prover tracks a column's kind only where `types` declares it and otherwise calls a string and a number unequal. A column compared with a string literal reads as a string and one compared with a number as a number; columns equated by a comparison, `JOIN ... ON`, `USING`, an `IN` subquery or a derived table's or CTE's projection share what is known about them; and a value that can be either (`COALESCE`, `IFNULL`, `GREATEST`, `LEAST`, `IF`, `CASE` branches, `NULLIF`) is both. A comparison that sets one kind against the other, a column that collects both kinds, or a mixed value used as a comparison, `BETWEEN`, `IN`, simple `CASE` operand or arithmetic operand is declined: `a.x = b.y AND a.x = 'abc' AND b.y = 0` returns the row where `a.x` is `'abc'` and `b.y` is 0 on MySQL (`'abc'` reads as 0), and `COALESCE(n, 'abc') = 0` is true for a NULL `n`. Declared types are read per table (`t.n` INT and `u.n` VARCHAR are different columns). Two declared columns of different kinds compared directly keep the opaque reading above. Strings and numbers are also known by the text for `LOWER`, `CONCAT`, `SUM`, `ABS`, `LENGTH` and the other string and numeric functions. On MySQL an untyped column is not assumed to be text when that matters (`kumo_sql_prover.numeric_column_reading`, issue #613): `n = 'x' AND n = 'y'` is empty for a text column but returns the rows where `n` is 0 for an integer column (verified on MySQL 8.0; `n = 'x' AND n <> 'y'` and `n IN ('x', 'y')` behave the same way), because MySQL compares a number with a string as numbers and reads both strings as 0. When one untyped column, or columns tied together by a join, `IN` or a derived table, or the same column of one table read under two names (`t AS a JOIN t AS b`: a key can make the two one row, so `a.n = 'x' AND b.n = 'y'` is one column compared with two strings; before 2026-11-11 the two names were two columns, and under a declared key on the join column that pair was proved empty), is compared with two different strings that MySQL reads as the same number (the leading numeric part, else 0), a proof counts only if the same pair also proves with those strings replaced by that number. A string that is not then a small integer (`'1.5'`) cannot be replaced, so the pair is declined. A column declared as text in `types` keeps its proofs. A column written without its table takes a declared type only when every table the query reads declares that name with one kind or, by the column list in `schema`, does not have it. `types` may declare only some columns, so a table that is read and does not mention the name may still hold it untyped, in this select or in another select of the query: with `t.s` undeclared and `u.s` text, `SELECT k FROM t WHERE s = 'x' AND s = 'y' AND EXISTS (SELECT 1 FROM u WHERE u.k = t.k)` returns the rows of an integer `t.s` that holds 0, and both provers proved it empty until 2026-11-10 because the bare `s` took `u`'s type. A bare name that exactly one derived table in scope can supply is tied to that derived table's column, so a type declared underneath is followed through the projection (`SELECT c FROM (SELECT s AS c FROM t) AS d WHERE c = 'x' AND c = 'y'` is empty for a declared text `t.s`); `tests/test_untyped_string_columns.py` holds both directions. Proofs that hold for either kind of column stay (`IN ('x', 'y')` against `= 'x' OR = 'y'`). DuckDB, PostgreSQL and BigQuery refuse to compare an integer column with a string that is not a number, so they are unchanged. A `SELECT *` or `t.*` in a derived table or CTE passes every column through (`d.x` is the `x` of each table the star reads), an unqualified column is the column of that name the query qualifies elsewhere, and each output column of a `UNION`, `INTERSECT` or `EXCEPT` (in a derived table, CTE, `IN` subquery or scalar subquery) is the column in that position of every branch (`tests/test_string_number_star_setops.py`, issue #613). Not covered: columns of a CTE with a column list, a star mixed with named projections in a set operation, a scalar subquery beyond its first projection, and dates against strings.
`tests/test_soundness_string_number_compare.py` keeps the witness (issue #542) next to the same-kind comparisons that stay proven.

[`tests/test_soundness_regressions.py`](https://github.com/wojoe-444/KumoSQL/blob/master/tests/test_soundness_regressions.py) and `tests/test_soundness_scope.py` keep each wrong proof found so far, with the database on which DuckDB shows the two queries differ, next to equivalent near misses that must stay proven. `tests/test_aggregate_rule_soundness.py` does the same for the aggregate, eager-aggregation and `DISTINCT` rules.

## A second attempt without the shape rules

Every normalization rule is an identity, so applying one can never make a proof wrong. It can still lose one. The prover compares two normal forms, and a rule that fires on one query of a pair and not on the other moves that side away from a form the two shared. The comparison of every eval against `main` for the 2026-11-10 batch found four proofs lost this way among several hundred gained: three engine test pairs (a filter above a `FULL JOIN`, against the same rows written as a `UNION ALL` of the two one-sided joins, where `wrapped_join_filters` pushed the filter on one side only) and one DLBench pair whose two texts are identical (`disjoint_union` wrote its `UNION` of two constants as `UNION ALL`, and a later step declines that derived table for its unnamed columns).

`src/kumo_sql_prover/shape_fallback.py` closes the class instead of the four cases. The batch's rules are *shape rules*: the normalizer applies them on the first attempt, and when that attempt ends without a verdict the pair is tried again with all of them off, which is the normalizer as it was before the batch. A proof or a refutation from the second attempt stands; otherwise the first answer is returned. This is the arrangement the keyed-`DISTINCT` levels and the semi-join reading already use. The module's docstring lists the shape rules. Two modules of the batch are not in the list because each only reads a query that was declined before it (`listed_output_names`, `printed_spelling`).

- What it guarantees: with the rules off, the steps taken are the ones taken before the batch, so a verdict that was reachable then is reachable now, up to the solver's time limit. It guarantees nothing about rules added outside the list: a new rule that rewrites queries the prover already read should be guarded with `shape_fallback.enabled()` in `normalize`.
- What it costs: the second attempt runs only for a pair with no verdict. Each of its steps normalizes both queries again with the rules off (the solver call is skipped when both texts are the ones the first attempt compared), and normalization is most of the time an unproven pair takes. Measured on undecided QUITE development pairs, it adds 0.1 to 0.5 s to a pair of under 1,000 characters, 1 to 2 s at 2,000 to 4,000, 5 to 25 s at 12,000 and up, and on one 36,000-character pair about 20 s and 1.7 GB. So the second attempt is made only when the two query texts together are at most 4,000 characters (`shape_fallback.MAX_CHARS`); the four lost proofs were under 700. A larger pair gets the first attempt only, and the guarantee above does not cover it.
- What it does not change: a refutation from the first attempt is final, and a proof from either attempt passes the same safeguards.

`tests/test_shape_fallback.py` holds made-up pairs of both lost shapes, and shows each is unproven when the second attempt is switched off.

## Proof search performance

Algebraic fallback levels reuse normalization within a single query pair and fixed proof context. The cached value includes normalization assumptions. Recursive and conditional proofs create separate caches, so different constraints, schemas, types and dialects never reuse a result from another proof. Solver calls and proof safeguards still run.

Model reuse does not submit a whole-view candidate when an explicit SELECT list has a different number of output columns from the view. A projection candidate still receives the full proof. Unresolved stars and set operations retain the conservative path. This avoids proving an impossible whole-view replacement without reducing the supported rewrite search.

Default-context Z3 proof entry points also defer automatic cyclic garbage collection while holding the solver lock, collecting pending cycles under that lock when needed before restoring the caller's GC setting. This prevents a different Python thread from finalizing old Z3 terms during a proof. Nested calls and exceptions preserve GC state. Direct external Z3 use or explicit concurrent `gc.collect()` is outside this serialization contract.

**Memory of a long proof.** With collection deferred, a call would keep everything it discarded until it returned, and Python frees a syntax tree only by collection (a node and its parent refer to each other). A 30-second normalization of a 16,000-character query that needs 200 MB held 3.2 GB that way, and four benchmark workers doing so at once were killed for memory on a 16 GB machine. The thread that holds the solver lock may collect, since no other thread is inside Z3 then, so it does: `solver_lock.sweep()` collects once 100,000 objects have been made since the last collection, and does nothing in a thread that does not hold the lock or when the caller had collection turned off. It is called for every select the normalizer visits, for every select and every error site the SMT compiler builds, where a solver is made and where a nested proof call ends. Objects made since the last sweep are collected each time; everything else only when ten times the duration of the last full collection has passed, so full collections cost about a tenth of the running time at most. Measured on four such pairs: 2.2 to 3.2 GB before, 190 to 230 MB after, in the same time, against 180 to 215 MB when collection is never deferred. A loop that runs long without passing one of those points still keeps what it discards until it does; a new long loop under the lock should call `sweep()`.
